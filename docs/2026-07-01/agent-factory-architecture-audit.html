读这份报告前先建立的一个心智模型
本系统里有两种 agent:(A) 最终交付、部署在 Inngest 上的业务工作流 agent(产品);(B) 在生成 A 的过程中干活的构建期 harness agent(工厂机器)。而 B 里的某些 agent 本身就是一个小型 harness —— 会推理思考、并决定是否生成 sub-agents / SKILLS / tools 来辅助完成自己的任务。整个系统因此是分形递归的。详见 §04。

04两类 agent 与分形 harness

这一节是理解整个系统最关键的心智模型。系统里的"agent"这个词指两种完全不同的东西,以及一种把它们连起来的分形递归结构。

A · 交付物 = 业务工作流 agent（产品）

最终生成、部署在 Inngest 上的 durable functions,由业务事件触发(如 RESUME_DOWNLOADED),感知 → 推理 → 调工具 → 产出业务事件。这是交付给客户、跑在真实生产里的东西。它们各自也有一个运行期 harness:step-engine 的 tool-use 循环、step.invoke 调兄弟 agent、emit 产出。

代码:register.ts / step-engine.ts。特征:durable、事件触发、多 agent 通过事件+invoke 协调。

B · 构建期 = harness agent（工厂机器）

在"生成 A 的过程中"干活的 agents。核心大脑 conductor 是 L1 harness(ReAct 循环),它调用一批专门的构建期 agent:understand_ontology(读懂本体)、critique_plan(挑战分解)、design_agent(设计单个业务 agent)、review_agent(审查)、codegen(生成代码)。它们不交付给客户 —— 是"造 agent 的 agent"。

代码:conductor.ts / tools.ts。特征:LLM 推理驱动、有反思/记忆/压缩、有预算。

你强调的点 · 分形:某些构建期 agent 本身就是一个小型 harness
构建期的某些 agent 不是"一次 LLM 调用"那么简单 —— 它会推理、思考,然后决定是否要动用下面三种"自我增强"能力来完成自己的任务:
  • 生成 sub-agents(ctx.spawn / design_subagent):当一个 agent 的任务太复杂,它拆出子 agent 辅助。子 agent 可以是临时的(运行期 CodeAct spawn,depth-capped、带 review loop)或被晋升为可部署的(design_subagent → 父通过 invoke 同步调它)。
  • 生成 SKILLS(create_skill):把可复用的决策规则 / procedural 知识固化成 skill,织进后续 agent 的 prompt,带 effectiveness 计数。对齐 Voyager 的"可执行 skill 库"。
  • 生成 tools(create_tool / doc→schema):当缺工具时,现造一个声明式 HTTP 工具,注册进目录供后续 agent 绑定。
于是整个系统是分形/递归的:harness → 构建期 agents → 某些 agent 自己又是 harness → 生成 sub-agents / skills / tools → 最终产出业务 agents。这正是文献里 harness engineering + agents-that-spawn-sub-agents + skill library 三者的组合。
审计相关性
这个分形结构解释了为什么"记忆写路径死"(§07.3)如此关键:构建期的 agent(通过 CodeAct ctx.memory)能用记忆,但交付的业务 agent 的租户工具因 ToolContext 无 memory 字段而用不了 —— 也就是说,分形结构在"构建期"通,在"交付物"的运行期断了一环。

08三问直答

(a) "context 放在 TS 里"是问题吗?

是,且精确是"水平扩展 + 重启存活"问题,不是单实例正确性问题。单进程内 Inngest step.run memoization 让它安全;进程重启与多实例会丢中途态、丢去重、无因果查询。三条替代见 §10。

(b) 反思/记忆/LLM 日志/agent 执行都落库了吗?

没统一。反思 ✓、runs/steps/tasks ✓、skills/tools ✓、大脑 transcript ✓;记忆在库但生产写路径死;原始 LLM 日志、per-tool-call trace、向量 embedding、协调 payload、验收 verdict 是文件或纯内存。完整矩阵见 §09。

(c) 每组件的评测/监控/调优搭好了吗?

设计时评测真实;运行时只有粗聚合、进程内、ephemeral 监控;调优闭环几乎不存在。盲区:大脑推理质量、per-agent 运行时、工具有效性回喂、记忆 recall@k、CodeAct 回退。对照 OpenTelemetry:缺 per-call gen_ai spans。

10持久化基质选型:Redis vs 数据库 vs 对象存储

"Redis 还是数据库"是个错误的二选一。它们是互补的两层 —— 真正要回答的是:哪一类信息,放哪一层。因为你现在放在 TS 里的东西,持久性、访问模式、生命周期各不相同,一刀切到任一单存储都会出问题。

三根决策轴

① 持久性

必须永久留存(审计/记录)? 可重算(缓存)? 还是"扛重启但不必永久"(工作态)?

② 访问模式

append-only 日志 / KV 点查 / 分析查询 / 向量相似 / pub-sub 扇出 / 原子计数?

③ 生命周期

永久 / 带 TTL / 临时?

逐类路由(你现在放在 TS 里的东西)

in-TS 状态现状应归属为什么
原始 LLM 日志纯内存,丢DB 专表 llm_callsappend-only、要分析查询(按 model 算花费/趋势);Redis 不适合审计记录
事件 ledgerNDJSON per-instanceDB event store 表要 durable/有序/可查询/可重放;真相源必须是 DB(规模化上 Kafka/Redis Streams 作传输)
大 blob本地 fs(已内容寻址)S3/GCS只换后端;RAM 装大 blob 错、DB BLOB 撑库
记忆 KV已在 SQLite保持 DB已经对了

大脑实时流 / EventBuffer内存 30k 溢出丢DB(transcript)+ Redis(pub/sub 扇出)DB 存真相、Redis 让多实例订阅同一条流

缓存(工具目录/域列表)in-process Map+TTLRedis 缓存现在 per-instance;放 Redis 变共享
我们系统的三个具体现实(决定了答案)
  • 已有 Inngest 做交付层持久执行 —— 它的 event history 本身就是交付层 durable 事件日志。所以"event store 缺口"主要是把那条独立的 NDJSON ledger 变 durable+可查询(DB 专表是务实第一步),不是从零造。
  • 现在是 SQLite 单实例(data/agentic.db WAL)。→ 单实例下引入 Redis 基本是过早优化 —— SQLite 已持久化大部分;Redis 的价值(跨实例共享/锁/扇出)只有水平扩展 N 实例时才兑现。
  • 真正"活在 TS 里、会丢"的是:大脑 conductor 内存循环(EventBuffer/向量 Map)+ 跨实例不共享的 ledger/blob 本地文件。原则:TS 内存只保当前进程操作的活跃工作集,凡有持久 or 跨实例需求的落 DB/Redis/S3。

分阶段建议

Phase 1(现在,单实例)· 只补 DB,不上 Redis

  • llm_calls + model_routing 表(G3)
  • event store 表(ledger payload 落库,G2)
  • acceptance_scores 表
  • ToolContext.memory 接线(G1)

SQLite 完全够用;此时上 Redis 只增运维负担、不解决真实问题。

Phase 2(要水平扩展时)· Redis 作热层 + 迁移

  • Redis:实时 SSE 扇出、分布式锁/run 归属、缓存、限流、并发登记
  • SQLite → Postgres(+ pgvector 做记忆向量)
  • blob → S3
  • ledger → durable event store(DB 表起步,规模化上 Kafka/Redis Streams)
一句话
DB 是真相源、Redis 是它前面的"快·共享·临时"协调层、S3 装大 blob。当下单实例,答案是"先把 DB 的洞补上"(尤其 llm_calls + event store 表 + memory 接线),Redis 等到真要多实例部署时再引入。这与文献里的 hot/cold 分层完全一致。

11七个跨系统承重缺口

被多个独立审计从不同视角同时命中的问题。

P0 G1 · 记忆生产写路径死

ToolContext 无 memory 字段(已核验),manifest 工具无法写。修复极小、误判风险大。

P1 G2 · 无 durable event store / 共享上下文

ledger per-instance 文件、blob 本地 fs、无因果图 → 最直接阻塞水平扩展。

P0 G3 · LLM 成本/路由/遥测 ephemeral

无法审计花费、验证 router、追回归。最高杠杆观测缺口。

P1 G4 · 反馈环不闭

验收/裁判/预算/成本表都测得到但不据此行动;裁判从不阻断 finish。

P1 G5 · subflow / 晋升是 stub

subflow fanout 无 emission(已核验);spawn→生产函数晋升未自动化。

P0 G6 · 无补偿/回滚/abort

硬失败后 emitted 事件残留(PAYMENT_INITIATED→无 CANCELLED)。正确性缺口。

P2 G7 · 静默失败面

condition 打错字静默 skip · payload_gap 只 warn 不阻断 · envelope 字段删除静默 · skill 原样织入(注入面)。检测到但不阻断。
