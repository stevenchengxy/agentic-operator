Agent 工厂是怎么搭出来的

把一份业务域 Ontology（对象 / 动作 / 事件 / 规则）变成一队真实可跑、经过沙箱验证的智能体——这本书拆开它的每一层：harness、agent loop、多智能体结构、模型路由、工具、记忆、沙箱与生产晋升。所有符号名都来自真实代码（packages/agent-factory · apps/api · apps/web）。

0它是什么 · 一句话与一张图

Agent Factory 是一个流式、工具驱动的自主代码生成 harness。核心是一个 ReAct 循环的 conductor（conductor.ts · runBrain()），它围绕一个业务域目标，自主地：读懂本体 → 规划 → 设计每个智能体 → 审查 → 让事件图闭合 → 部署到 Inngest 沙箱真跑 → 交付。整个过程以 SSE 事件流实时推到前端。

图 0 · 端到端：Ontology → 自主设计 → 沙箱真跑验证 → 生产晋升，全程 SSE 直播
两条事实地基。 ① 本体是唯一事实来源——事件名/动作名/字段名/工具名全部从 read_ontology 来，约束解码（grounding enums）禁止模型脑补不存在的符号。② 沙箱是唯一验收标准——只有真实部署到 Inngest 并端到端跑到成功终态（或合法的外部交接终态）才允许 finish。

1Harness 系统 · 运行的生命周期

一次工厂运行从 GET /v1/agent-factory/stream?domain=X&goal=Y 开始。API handler 调 startRun()，在进程内的 run-registry 注册一个 ActiveRun，并脱钩（detach）一个后台 driver 去跑 runBrain()。关键点：浏览器关掉 EventSource 只是取消订阅，运行本身在服务端继续——所以刷新/重连能接回还在跑的 brain（靠 run.started 帧里的 runId + localStorage）。

组件职责位置
run-registry持有 ActiveRun；订阅者重放尾部缓冲；EVICT_AFTER_MS 回收；镜像到 factory_runs 持久化apps/api
startRun / drive脱钩后台 driver，把 runBrain 的 yield 帧广播给所有订阅者apps/api
ConversationStore每轮把 messages + ctx 快照存 factory_conversations → 重启可续跑port
SSE 契约useBrainStream：run.started 捕获 runId；done 解锁；60s 静默看门狗解僵尸apps/web
非崩溃安全。 Inngest dev 模式不是崩溃安全的：若 api 在运行中重启（tsx watch 改文件触发），在飞的 handler 可能被丢；前端的静默看门狗会在 60s 无帧后解锁 composer，避免卡在「发送没反应」。

2ReAct Agent Loop · 推理的心脏

runBrain()（conductor.ts，约 480 行）是一个 async generator。它装好 BrainCtx（累积所有状态：specs / ontology / currentPlan / testCases / lastSandbox / humanDirectives …），从 [system, user(goal)] 起步，进入主循环（上限 MAX_TURNS）。

图 2 · ReAct 单轮：选模型 → 流式推理 → 工具派发(约束解码) → 结果回灌；穿插 HITL 暂停门

约束解码（grounding enums）

派发前，injectGroundingEnums 把工具 schema 里的「动作名 / 工具名」字段约束成真实本体符号。如果 design_agent 仍发明了一个不存在的名字，工具失败后会注入一条系统消息把真名喂回去，让 brain 自我纠正——这是「不写死、但也不许胡编」的关键机制。

3多智能体架构 · 一个指挥 + 专项子代理 + 两条执行路

工厂不是「一个巨型 prompt」。它是一个 conductor 主脑 协调若干专项子代理与两条运行时执行路径。

主脑 · Conductor

唯一的 ReAct 推理体，持有全局 ctx，决定下一步调哪个工具。它就是推理本身（streamTurn）。

子代理 · 测试用例设计师

test-cases.ts · authorTestCases：独立的 chatOnce 调用，按事件链造 pass/reject/edge 用例（真·LLM）。

子代理 · 质检裁判

review_agent Tier-2 / analyze_failure：独立 review-tier LLM，引用证据片段挑问题。

子代理 · 压缩摘要器

summarizeDropped：fast-tier LLM，把折叠掉的早期对话压成「决策+原因」要点。

两条运行时执行路径

图 3 · 同一个生成出来的 agent：默认走声明式 manifest；当渲染代码通过编译+安全 lint 时，沙箱里真跑 CodeAct，失败自动回退声明式（永不破坏验收）
声明式 vs CodeAct 的取舍。 声明式是生产标准（100% spec 驱动、可重放、可审计）。CodeAct 让「生成的代码真的执行」，但只在 -sb 沙箱租户里、且 runGeneratedCode 设计成永不抛异常——任何失败返回 null，step-engine 自动回退声明式。所以打开它不会让已经能跑通的链路回归。

递归 harness · 一层套一层

harness 是层层嵌套的：顶层大脑管 Agents/Skills/Tools；每个部署出来的 agent 自己也是一个 harness（跑工具循环）；agent 还能调子 agent。三层加上新的运行时自生成层：

图 3b · 递归 harness 四层。L1.5 是可部署的子 agent（生产路径）；L2 是运行时自生成的沙箱助手
和「必须可部署」怎么调和（已实现闭环）。 交付物永远是 L1/L1.5 的静态注册函数（可重放、可审计）。design_subagent（新）让大脑把一个复杂父 agent 拆成 父+可部署子 agent：给父的 plan 加一个 kind:"invoke" 步（idempotencyKeyFrom+软失败），子 agent 是真实注册的函数、被父同步调；子 agent 不计入本体覆盖，但受 has_code/tools_resolve/sub_agents_bound（不能有没人 invoke 的孤儿）验收。L2 的 ctx.spawn 运行时生成+跑临时子 agent 用于沙箱辅助 / 发现值得固化的子任务——它生成的代码被 spawnedSubAgents 捕获，直接喂给 design_subagent(code=…) 就晋升成可部署子 agent（过 TS+安全 lint）。发现 → 固化 → 静态调，闭环打通；「能自生成」与「最终可部署」都不牺牲。

4推理 / 审查 / 反思 · 哪些是真 AI，哪些是确定性护栏

用户最关心的一点：不是写死的，是真由 AI 推理。事实是——推理本身就是 conductor 的 streamTurn（真 LLM）；工具大多是「校验 + 落地」的确定性护栏（这恰恰应该确定）。下表逐个标注：

机制性质说明
streamTurn / chatOncereal-LLMOpenAI SDK 流式打到网关；所有推理的底座
modelChain / tierForContext配置驱动按阶段选 tier；模型 id 来自环境变量或实时 catalog 派生，无硬编码
understand_ontology 🆕real-LLM读完本体显式消化成结构化理解（要造谁/事件链/规则闸/外部交接/歧义），存入 ctx 并贯穿设计
critique_plan 🆕real-LLMreview-tier 独立挑战分解：漏/多 agent、顺序、闸口认定、外部交接误判、跨 agent 契约
review_agentdet + real-LLMTier1 确定性集合检查 + Tier2 LLM 裁判（必须引用 prompt 证据片段）
analyze_failuredet + real-LLM当 brain 给的根因太薄时，调 LLM 从真实运行态合成根因+可执行教训
generate_test_casesreal-LLM测试用例设计师 LLM；无网关时回退确定性 golden fixture
create_plan / design_agent推理在循环里 + det 落地规划/设计的推理发生在 conductor 的 streamTurn；工具负责 grounding/校验/渲染
score_specdet4 维打分纯公式（工具解析率/prompt 丰富度/决策覆盖/精修健康）——刻意确定
这一版新增的三道真·推理闸。 understand_ontology（答「我怎么知道 AI 读懂并记住了」）、critique_plan（答「规划没人挑战」）、流水线强制 review_agent（答「设计后没有审查反思」）。三者都发 reflect 事件，前端实时显示「🧠 反思：…」，形成可见的思考时间线。

5模型路由 · 按任务难度灵活选模型

tierForContext(ctx) 按阶段选 tier，modelChain(tier) 解析出一条「首选→兜底→base」的链，streamTurn 依次尝试直到某个模型成功。链要么由环境变量钉死，要么从实时 catalog 按偏好模式派生——没有硬编码模型 id。

阶段tier典型模型偏好
读本体（无 plan 无 specs）fastflash / haiku / mini
规划（有 plan 未设计）defaultgemini-3.1-pro / gpt-5.4 / sonnet
正在设计（specs < 计划数）hardsonnet / kimi / gpt-5.4 / opus
设计完成后的轻活default回落，不再钉 sonnet
评审/裁判/失败诊断reviewopus / gpt-5.5（裁判最贵，错判代价最高）
修过的坑。 旧版 tierForContext 是单向棘轮：一旦设计了第一个 agent，之后每轮都钉死在 hard 链首位（永远 sonnet-4.6）。现已改成阶段感知：读=fast、规划=default、设计中=hard、设计完=default，所以一次运行会用到 flash + pro + sonnet 多个模型。

6工具注册表 · BrainTools vs 运行时工具

BrainTools（设计期）

FACTORY_TOOLS：conductor 能调的 ~34 个工具——read_ontology / understand_ontology / create_plan / critique_plan / design_agent / review_agent / sandbox_run / supply_test_data / finish …。这是 brain 的动作空间。

Global Tool Registry（运行时）

packages/tools：生成出来的 agent 在运行时能用的工具（fs.* / http.fetch / parseResumeApi …）。配置驱动，任何租户的 manifest 列名即用。

解析顺序（step-engine）：租户专属 ?? 全局注册表 ?? MCP 工具。manifest 的 tool_use[] 是信任边界——注册了不等于可调，必须在白名单里。search_tools 让 brain 按语义检索真实工具；create_tool / extract_api_schema 能把一篇 API 文档现造成工具。

7Memory 管理 · 写入 / 召回 / 压缩

记忆分三层，关键区分是「写入」与「真正被召回进推理」。

图 7 · 记忆生命周期：写入 → 召回进 system prompt / 折叠摘要 → 2 层压缩；open-problems 锚点永不丢

反思（reflections）是真召回的：开跑时按 kind 优先级（failure>caveat>success）取 Top-5 注入 system prompt，实现跨运行学习。压缩 Tier2 是真 LLM。这一版补的洞：understand_ontology 的 AI 消化结论也进了折叠摘要，所以早期对话压掉后，设计阶段仍能从「读懂的模型」推理（「读了就忘」保险）。

向量召回已落地（原 v1 桩）。 运行时 agent 的 ctx.memory.search(query,k) 现在接了真实 MemoryDriver（createLocalVectorDriver）：默认本地确定性 embedding（词 token + 中文 unigram/bigram → 256 维哈希向量，L2 归一化，离线可复现），按 cosine 相似度排序返回 top-k；按 MEMORY_EMBED_MODEL 可切换到网关 embeddings（openaiEmbedder，OpenAI 兼容 /embeddings）。租户隔离在 SQL 边界（MemorySearchScope 由 SDK 透传），跨 subject 语义召回。行向量按 (key+updatedAt) 缓存，一次编码多次复用。bootstrap 自动注册（MEMORY_VECTOR=off 可关）。进一步：持久化 embedding 列 + SQLite-VSS/pgvector ANN 索引以支撑超大语料。

9生成代码的真实执行 · CodeAct

design_agent 渲染出每个 agent 的可读 .ts，然后 renderExecutableCode 给它评级：用 TS 编译器校验 + 安全 lint（禁 child_process/fs/net/eval）。两关都过 → spec.codeExecuted=true。manifest 映射：codeExecuted = codeSource==="ai" || spec.codeExecuted。

运行时（step-engine 的 logic 动作）：若 codeExecuted && typescriptCode，调 runGeneratedCode 真跑转译后的 handler。它永不抛异常——门控不满足（非 -sb 租户、或代码无效、或运行出错）就返回 null，step-engine 回退到声明式 prompt 路径。所以「让生成代码真执行」是尽力而为 + 自动兜底，不会破坏已验证的链路。

实测。 打开 FACTORY_EXEC_GENERATED=1 跑 Agents-generation：6 个 agent 全部评级 codeExecuted=true（渲染代码编译+安全检查通过），且 finish 照常达成——零回归。

11晋升到生产

沙箱跑通、finish 把 agent 存成可审阅的草稿后，promote 把同一套 manifest 注册成一个真实的生产 Inngest app（每个业务域一个 app：agentic-operator-<域>），生产路径走声明式执行（CodeAct 的 -sb 门控自动让生产回落声明式）。生产里只反映通过 POST /v1/events 打进来的真实事件——零 mock。

一句话收尾。 设计期的智能（conductor + 真 LLM 推理 + 三道审查闸）负责「造对」；沙箱的真实部署+自适应观测+验收门负责「证明能跑」；生产的声明式 manifest 负责「可重放可审计地运行」。三段各司其职，就是这个 harness 的全部。
