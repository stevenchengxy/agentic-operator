04Part II · ReAct 架构判决:不推倒,升级为"分阶段 plan-execute、阶段内 ReAct"

现状:单层扁平 ReAct 循环暴露 38 个工具,流水线次序只靠 system prompt 的散文引导("别跳过""先 X 再 Y");三个独立轮询 HITL 门;MAX_TURNS=200 是唯一硬背板(token 无硬上限是你本人否决过的刻意决定,soft 成本表是补偿控制 —— 这点不算 bug,但要认识到它把控制责任压到了 nudge 机制上)。

脆弱性证据(代码里"纠正 LLM 选择"的补丁密度):规则闸口强制 floor 绑定、覆盖 nudge 循环(耗尽 5 次后放弃)、compaction 叙事 LLM 失败静默回退 ""、review 只能事后抓、相同工具重复调用无护栏。这些补丁每一个都是"扁平循环管不住次序"的症状。

判决
ReAct 本身不是错的 —— 错的是把"阶段推进"也交给它。正确形态:外层 = 显式阶段状态机(plan-execute),阶段有入口前置条件和出口闸门;阶段内 = ReAct(设计/修复这类开放任务仍需自由推理)。这与 DeerFlow 的 StateGraph+StepType 路由、也与我们已有的 phaseFor 信号(只差"从展示信号升级为控制闸门")同构 —— 迁移成本低:把 phaseFor 从 UI 标签变成阶段准入检查即可起步。

配套修复:① compaction 叙事 LLM 失败时改为确定性截断兜底 + 发 warning 事件(不再静默丢推理连续性);② 相同工具+相同参数重复调用检测(2 次即打断,给结构化提示);③ 每阶段 token 预算(PLAN 50k / DESIGN 500k / VALIDATE 100k / SANDBOX 150k,超限升级 analyze_failure 而非磨)—— 这是"阶段预算",与你否决的"全局硬上限"不同,建议采纳。

05Part II · ask_user / HITL 统一架构

现状盘点(4 条路径,3 个独立轮询门):ask_user 澄清门、测试用例批准门、边界事件门(各自 awaiting* 布尔 + 150-tick 轮询 + 超时自动放行)+ supply_test_data(复用澄清门)。核心缺陷:消息队列是扁平的 —— 用户回复没有目标标签,先轮询到的门先消费;答案可能被错误的门吃掉 → 该门超时走默认值(错误决策),真正提问的门永远等不到。加上 4 处超时/回退语义各自为政、前端 4 套 UI 接线。

迁移路径(低风险):先加 InteractionRequest 信封与 id 路由(三个门内部照旧,只是消息带上目标 id → 立即消灭误抢);再合并超时/回退语义;最后前端合并为单组件。选项回答 value 化(radio),free-text 只作显式 "other"。

10DeerFlow 及开源对比:借编排形状,不换栈

研究对象:bytedance/deer-flow(已从深度研究框架演化为 "SuperAgent harness":lead agent + 子 agent + 沙箱 + 记忆 + skills + 消息网关)及其经典研究工作流(LangGraph StateGraph 九节点)。

DeerFlow 机制判定对我们的含义
类型化 Plan + StepType 路由:planner 产出结构化计划,步骤按类型路由到 researcher/coder✅ 借鉴正是 §04 的方向:阶段推进用结构而非散文。我们的 plan[] 已类型化,缺的是外层用它驱动控制流

LangGraph/LangChain 栈❌ 不借我们的持久层是 Inngest(durable functions 本身就是交付物),换栈零收益、丢 durable 语义
交付形态:报告/artifacts(research reports、slides、dashboards)❌ 方向不同我们交付可部署、事件驱动、durable 的生产 functions——验证 spine(沙箱真跑+验收 bar+code_ran 回执)是我们独有且必须自研的部分,DeerFlow 没有对应物
结论
DeerFlow 方向部分契合、值得借三样东西(类型化计划驱动控制流、人审一等节点、子 agent 上下文隔离)—— 三者恰好分别印证本报告 §04/§05/§08 的三个核心建议;栈与交付形态不契合,不迁移。
