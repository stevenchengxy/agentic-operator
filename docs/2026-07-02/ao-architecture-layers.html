1. 全景：五层架构总览apps/web · apps/api · packages/*

整个系统是一个 pnpm monorepo 的双进程平台：Next.js 前端（:3599）零数据库访问，一切读写经 /v1/* 代理到 Fastify API（:3540）；API 之下是两块大引擎——生成 functions 的多 agents 系统（协调者 + 内部角色 + 嵌套派生的工厂车间）和 Agent 运行时（跑已交付 functions 的 Inngest 事件引擎），共享同一套数据层。

每层一句话

层职责关键约束
L0外部世界知识（Allmeta 本体）、算力（LLM）、持久执行（Inngest）、业务能力（SaaS API）、渲染（Chrome）一切外部输入都是数据不是指令；PDF 打印进程断网
L1展示层纯投影：同一条 SSE 事件流渲染出聊天流、右栏、后台面板——历史回放与实时渲染同构零 DB 访问；回答/介入只走聊天流一个入口
L2接入层认证 + RBAC + 租户隔离 + 审计；把 HTTP 世界翻译成端口调用（makeFactoryPorts 组合根）每张业务表带 tenant_id；dev 模式才认 x-agentic-tenant
L3a生成多 agents 系统协调者读懂意图后分派内部角色（理解/规划/设计/验证/交付）；角色能力不足即嵌套派生（认知专家 ∥ 并行 / 子大脑递归）；共享一个推理核；产物是 functions纯包，不碰 DB/HTTP——一切依赖经 FactoryPorts 注入；意图/介入/理解三样记忆恒存
L3b运行时把交付的 agent 变成 Inngest 持久函数：事件触发、工具循环、代码真执行、HITL所有 DB 写包在 step.run 里（重放恰好一次）
L4数据层SQLite（33 表）+ data/ 文件（日志、草稿、本体、报告、产物）runs.agent_id 是 RESTRICT 外键——历史不许被裸删
核心设计观：工厂与运行时是「造飞机的工厂」和「机场」的关系——共用跑道（数据层与事件总线）但绝不混淆：草稿永远不会静默变成生产 agent，晋升是显式、增量、可审计的一步。而工厂本身不是一个大脑加一堆工具，而是一支车间班组：协调者分工、角色作业、人手不够就现场派专家。

1.5 两套系统，一个共享基座（本书的总纲）

把五层图再抽象一步，全平台是两套各自完整的多 agent 系统：系统 A（生成系统）——造 functions 的多 agents 车间；系统 B（交付系统）——functions 跑业务的运行时。两套系统各有自己的 agents、自己的 sub-agents、自己的 CodeAct，绝不混淆；靠两座桥连接（晋升桥、固化桥），踩在同一个基座上（数据层、工具资产、HITL、观测），并由一条回流飞轮让 B 的运行经验反哺 A 越造越好。

同构性原则：A 与 B 是同一个模式——「选型 → 能力不足即派生 → 执行 → 经验回流」——在两个域的实例。这不是巧合而是设计：会造 agent 的系统自己就该像一队 agent 那样工作。

3. Harness：离体运行的大脑run-registry.ts · conductor.ts · stream-gateway.ts

Harness 是系统 A（生成系统）的宿主进程形态。它的第一性设计是「大脑与浏览器解耦」：点开始后，大脑在 API 进程内的 run-registry 里离体运行——关掉页面它继续跑，回来重连即重放。这就是右上「后台任务」面板能存在的根基。

回合起点的意图门（理解你，而不只是执行你）

每次带新 goal 进入运行（新会话或续会话补充），主循环先用 fast 档做一次意图解析：把用户的话理解成「意图类型（生成/分析/修改/提问）+ 关键约束 + 期望产物」，追加进 ctx.userIntent 并以 💡 反思卡呈现在聊天流——你能看见大脑是怎么理解你的，理解偏了当场纠正。之后每一次 [人工介入] 既全文进上下文，也累积进 humanDirectives；意图与介入都是折叠幸存者（见 4.5），无论对话多长、折叠多少轮、API 重启多少次，大脑不忘你说过什么。

4. 推理是怎么推理的ReAct 循环 · 理解门 · 评审门 · 模型分层 · 反思记忆

大脑不是「一句提示词走天下」，而是一个带结构化自我怀疑的 ReAct 循环：先显式消化本体（understand），方案先被独立评审（critique），设计后打分（score），退步就回滚（revert），跑完留反思（reflection）供下次运行开局注入。

为什么「理解」和「评审」要做成工具而不是提示词？提示词的要求会被折叠冲掉；做成工具后产物落进 ctx.ontologyUnderstanding（折叠时强制保留）与 reflect 事件（进 UI 与反思库）——「读了就忘」被结构性堵死。critique_plan 曾在真实运行中抓到事件链断裂并触发 4 轮方案修订。

4.5 嵌套 Harness 与共享推理核：生成 functions 的多 agent 系统

工厂内部本身就是一个多 agent 运行时：conductor 是协调者，「理解 / 设计 / 验收」是内部工作角色；任何角色能力不足时都可以嵌套派生。派生分两条通道，但共用同一个推理核（同一套模型路由、降级、遥测、记忆读口）——「共用一个推理大脑」指的就是这件事：专门化的是角色与上下文窗口，不是另起炉灶的模型设施。（注意这是系统 A 的推理面；系统 B 的 functions 走 llm-gateway——同底不同面，见图 1-2。）

嵌套通道形态适用成本
轻通道 · 认知专家（specialists）带角色提示词的单/少跳结构化调用，可并行，产出 JSON 汇总回主线数据已在手、需要专注消化的子问题（四维分治理解本体、意图解析等）每个专家 1 次 LLM 调用
重通道 · 子大脑（spawn_subagent）完整 runBrain 递归：自己的消息史 + 只读工具集 + 多回合需要自主取数、多步推理的独立研究任务一个小型运行（深度 ≤ 2 防爆炸）
三个折叠幸存者（上下文记忆永不丢）：userIntent（意图门对用户目标与随时补充的结构化理解，追加式）、humanDirectives（全部 [人工介入] 累积）、ontologyUnderstanding（四维分治的汇总结论）。三者都写进折叠摘要，且 serializeCtx 全量落 factory_conversations——折叠不丢、API 重启也不丢。

5. Agent 生成流水线6 阶段 · 角色作业 · CodeAct 分级 · 验收闸

右栏顶部的阶段轨（读业务→规划→设计→校验→试运行→交付）背后是这条流水线——每个阶段由一个内部角色 agent 作业（理解角色、规划角色、设计角色、验证角色、交付角色），任何角色遇到消化不动的子问题都可按 §4.5 派认知专家或子大脑。核心原则：「跑通」= 真沙箱里生成代码真执行 + 整链事件真流转 + 用例逐个有判定，缺运行证据时 finish 会被验收闸拒绝。

别忘了系统 A 自己的 CodeAct：流水线的每一步"造与验"本身就是代码在干活——编译、AST 安审、加载探针、事件图闭合计算、沙箱驱动，全是系统 A 的确定性执行面；LLM 只在需要判断的关节出手。这与下面讲的"产物 CodeAct"（系统 B 里 function 的执行范式）是两回事。
CodeAct 分级为什么重要：「生成了代码」≠「代码真的会跑」。只有过了编译+AST 安全 lint+加载探针的代码才标 ⚙ CodeAct 并在沙箱里真实执行、在 runs.code_ran 留下回执；没过的诚实降级为 📄 声明式并标注探针原因——验收闸读的是回执，不是宣称。

5.5 design_agent 的内部 ReAct 循环（内推演，把外层回环前移）

真实轨迹里出现过 8 次修订回环：设计角色先交草稿，再靠外层 review→refine 反复挨打（同一批问题——规则硬编码、分支没覆盖、字段没透传——被 review_agent / review_context / review_completeness 每轮重复标记）。根因是审查发生在提交之后。design_agent 现在有一道提交前的内部循环：draft → 确定性自检（零 LLM）→ 命中硬问题就跑一次内部精修 → 提交改进版。

为什么"确定性自检 + 一次 LLM 精修"而不是"内部多轮 ReAct"：最常打回的三类问题（分支没覆盖全、非闸口 agent 写死规则、prompt 出现本体没有的事件名）都能零 LLM 确定性查出；查出后一次针对性重写就够，多轮内部 ReAct 只会重复外层已有的 review→refine 而徒增开销。省下的不是判断，是"把判断写得好看"的来回。

6. Sub-agent 的三类，两条交付路径认知分治（工厂内部）· design_subagent（设计期固化）· ctx.spawn（运行期涌现）

先分清三类 sub-agent（名字相同，分属两套系统）：① 认知分治型（系统 A 域）——内部角色能力不足时派生的「工人」（如四维分治的 objects/rules/actions/events 专家），服务于推理本身，见图 4-2，永不进交付物；② 设计期固化型（系统 B 域）——交付物的「零件」，父 function 拆出的可部署子 function；③ 运行期涌现型（系统 B 域）——产物 CodeAct 执行中即席孵化的子代理。本章讲 B 域的两类；③→② 走固化桥（回系统 A 经 design_subagent 验证），是 A/B 之间除晋升桥外唯一的通道。

交付侧的「层层嵌套」：一个复杂父 agent 可以拆出可部署的子 agent（设计期），生成代码在运行中也可以临时孵化子代理解决子问题（运行期）——后者若被验证有价值，还能被固化晋升为前者。

7. 工具体系：两套工具、四级解析packages/tools · factory_tools · MCP

这是最容易混淆、也曾真实踩坑的地方（大脑试图直接调运行时工具失败后徒手写 HTML）：大脑的工具（怎么造 agent）与运行时的工具（agent 干活用什么）是两套体系，各有目录、各有解析规则，通过「设计期绑定 + generate_report 这类桥接工具」互通。

8. Agent 之间怎么沟通事件驱动 · 信封+blob · invoke · subflow · 补偿

本章讲的是系统 B 的通信。系统 A 内部（协调者↔角色↔专家）不走事件总线——它们靠 BrainEvent 冒泡 + ctx 共享状态通信（同进程、同一条 SSE 流可见）。两套通信机制的对比见 §1.5 总表。

交付后的 agents 之间不直接互调——一切经 Inngest 事件总线：上游 step.sendEvent 发 ${租户}/EVENT_NAME，下游函数以之为触发。这带来天然的持久性（重放恰好一次）、并发控制（按 subject 串行）与可插拔（新 agent 订阅既有事件即可加入链路）。

9. ask_user 与人机协作三门一邮箱 · 唯一动作面 · 双向回传

HITL 也是两面的：本章主体是系统 A 的协作面（生成过程中的问答与介入），章末是系统 B 的人审面（生产链路的 tasks 停机点）。协作设计的铁律：聊天流是唯一的问答与介入通道；右栏与后台面板只做「看见」与「引导回聊天区」。大脑的提问是结构化的（选项 + 推荐 + 上下文），用户的回答经标签路由精确回到提问的那扇门。

运行时的 HITL 是另一条线：已上线 agent 遇到需要人审的动作时，创建 tasks 行并 step.waitForEvent("task.resolved") 持久等待——「人工任务」页处理完毕后链路自动续走，等待跨小时/天都安全。

10. 报告管线：确定性分析 + LLM 叙事generate_report · report-jobs · reportGenerator

报告管线是系统 A 的旁路产物线——由 A 的 generate_report 触发、复用共享基座的 artifacts/CSP 设施与 B 面的 reportGenerator agent。血泪换来的设计哲学：判断下沉到确定性计算层，LLM 只做业务解读。事件分类、断链候选、并发扇出、规则全量聚类全部由代码算好并以自描述中文喂给模型；模型受「数据忠实性契约」约束（名词/编号/数字必须逐字来自数据）；方法论附注由服务端确定性追加，不依赖模型自觉。

11. UI 信息架构：三层各司其职聊天流 · 右栏 · 后台面板

三个面各回答一个问题、绝不重复：聊天流答「现在对话到哪了、我该说什么」；右栏答「这次运行造出了什么、质量如何」；后台面板答「后台都在发生什么」。
