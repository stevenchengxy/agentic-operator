Agent 工厂 · 最新技术架构报告

本报告描述 Agent 工厂当前实际构建完成的架构（区别于此前的优化提案报告——那份记录的是"要改什么"，这份记录"现在是什么"）。核心形态：一个共享推理 harness 的生成系统（系统 A），把业务本体编译成部署在 Inngest 上、带载荷契约与执行保真验收的业务 functions（系统 B）。设计定稿三原则：原生 AI 推理（系统只供给事实与建议，推理决策全部在 AI 手里）、契约只钉在 wire 上（functions 之间的载荷契约是唯一的硬 schema）、协议封闭 · 认知开放（事件协议与验收判据封闭，认知词汇全部开放生长）。

一句话架构：用户目标 → 意图门 + 前置路由（按意图选流水线形状）→ 共享 ReAct harness 在阶段闸门内自主推进（读本体 → 理解 → 规划 → 评审 → 逐个设计 agent → 校验 → 真实沙箱 → 定点返工）→ 10 判据验收 → 晋升为 Inngest functions。全程三条硬底线：事件/工具/字段必须真实存在（防幻觉）、emit 载荷必须满足下游契约（防 output_parse_error）、验收只认真实执行证据（防"看起来跑通"）。其余一切——分治深度、是否拆子 agent、何时问用户、如何回应本体缺失——都是 AI 的原生推理决策。

2原生 AI 推理层（#NATIVE 定稿）

定稿原则：系统绝不替 AI 做推理决策。所有曾经的确定性推理开关（本体规模阈值→强制四维分治、difficulty→强制深评）均已移除；系统的职责收敛为三种——供给事实、呈递建议、验收产物。

3本体：投影 · 编译 · 锚定（工厂内部不建本体）

业务层本体是唯一的本体（外部输入：actions / events / dataObjects / rules），工厂对它只做三个动作；工厂内部没有任何"小本体/认知框架"。

动作做什么刚性
投影按任务切相关子图给理解/规划——只读；AI 可质疑、可标歧义、可提修订开放
编译event_data → wire 载荷契约；规则闸 → 运行时 ontology.fetchActionRules 动态拉取（规则永不写死进 prompt）硬（面积最小）
锚定心跳式 re-grounding，保证整个运行过程"永不忘本体"开放

3.1 分层查找与未命中的原生反馈

本体来源三层：租户上传的本体（📎 上传 actions/events/dataObjects/rules JSON 即建新域，租户内立即可用）→ 本地 models/ 域 → live Allmeta（UploadedFirst(Uploaded, Composite(Allmeta, Manifest))）。未命中不写死任何分支话术：read_ontology 把事实摆全——底层错误原文、各来源合并后的可用域清单、"平台支持上传 JSON 建新域"的能力事实——怎么向用户解释/引导由 AI 推理组织。唯一硬约束：别编造本体、别不告知就换域。

3.2 修订提案回路 #REVISION（本体不是只读的）

真实沙箱载荷与 canonical 持续不一致 = 本体漂移证据：ontology-revision.ts 确定性对账出 retype_field（类型漂移，全部观察一致才提案）/ add_field（持续携带的未声明字段）提案，emit ontology.revision 事件 + 引导 AI 走 ask_user 与用户确认——"AI 提案 → 人确认 → 生效"，与边界事件门同一范式。v1 只提案不写回（确认后写回上传本体存储 / Allmeta diff 是待建项）。

本体漂移的另一处信号：read_ontology 会对本体做签名（动作/事件/对象/规则计数），re-read 时签名变化 → 显式警告"已设计的 specs 基于旧本体"。

4交付判定 + 调试坐标系（原"契约脊柱"，已按最终定位改名）

这一层不是"契约理念"，而是两件具体的东西："跑通"的可判定定义（真实 emit 的载荷下游真的能用——没有它，"跑通"退化为"链到终态"，即历史上 output_parse_error×78 的假跑通）和失败定位的坐标系（LLM 读日志归因仅 53.5% 准，答案必须确定性算出来）。数据流四段，全部纯函数可单测：

#段机制代码
1契约图（生成期）
提醒·不阻断		specs × canonical event_data 对账出 payload_gap / type_mismatch / type_conflict（冲突降级 unknown 保证顺序无关）。#NATIVE 定稿：设计期契约问题一律是【高置信事实提醒】，不翻 validate 的 ok、不阻断推进——双方 schema 都是 AI 自己声明的，冲突=自相矛盾，提醒即修；AI 无视提醒 → 沙箱真实失败 + 归因把它带回来。仍翻 ok 的只有结构性事实（覆盖缺口/事件图不闭合/无工具——"链根本不可能跑"）contract.ts · tools.ts validate_graph
2执行保真（运行期）对真实沙箱 I/O 评估：真实 emit 的事件名 + 从事件账本（payloadRef=path#offset）读回的真实载荷（不是最后一步输出、不猜 emit[0]；无 emit → 不评）。canonical 字段 required、consumer 自造字段仅有则查型；同指纹重跑保留最强证据（不洗白违约）execution-fidelity.ts · sandbox-deployer.ts
3失败归因 #ATTRIB保真违约 × 契约图确定性 join → 逐 agent 定点指令（refine_producer / align_contract / ask_user + 受影响下游）——论据：LLM 读日志归因仅 53.5% 准，答案必须算出来failure-attribution.ts
4补偿 #SAGAspec.compensationEvent → manifest compensation_event → 运行时硬失败幂等 emit；设计自检对"有副作用工具却无补偿"软警告design-loop.ts · register.ts
为什么这层必须存在：实证锚点——历史 10,780 次运行中生成 agent 的代码从未真正执行、主导失败是 output_parse_error（emit 载荷不满足下游 schema）。运行期保真裁定 + code_really_ran 验收，就是针对这组事实建的"跑通"定义；生成期对账只是让 AI 更早看见问题的提醒，不是门。
