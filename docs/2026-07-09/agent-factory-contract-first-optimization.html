Agent 工厂优化 · Contract-First 双系统架构 · 学术支撑 · Codex 蓝图审查

本报告基于对新旧两个 repo 六个生成 / 六个在跑 functions 的实证分析、三轮学术检索（20 篇经对抗核验 + 14 篇经典/已知补充）、以及对 Codex《Ontology-Guided Dynamic Prompt & Subagent Planning》蓝图的逐层审查，给出一套优化方案。核心结论一句话：工厂当前真正卡住"跑通"的不是 prompt 质量，而是运行期契约保真度——10,780 次运行里只有 6 次真正执行了生成代码（且全是手写 agent），主导失败是 output_parse_error（emit 载荷与 schema 不符）。因此优化的脊柱应该是契约（Contract），而非 Prompt Ledger；蓝图把最大投资押在了错误的瓶颈上。

你问的三件事——(1) 让工厂能理解并拆分用户问题、判断该用什么推理方法；(2) 把 ask_user 从"泛化提问"做扎实；(3) 为"agent 间通信 + 交付可部署 Inngest functions"找到架构级论文支撑——都指向同一个更深的问题：工厂现在能"生成"agent，但生成物离"真正能跑起来的业务流程"还差一层运行期保真。下面是四条贯穿全文的判断。

判断一瓶颈定位错了

Codex 蓝图把 80% 篇幅投在 Prompt/Payload Compiler + Ledger + Lint + 版本回滚。但实证数据显示：生成 agent 从不执行自己的代码，失败是 output_parse_error——这是运行期数据契约问题，不是 prompt 措辞问题。再漂亮的 prompt 也修不了"emit 出来的对象下游 parse 不了"。脊柱应是契约，Prompt Compiler 是叶子。

判断二两套系统要用一根契约脊柱缝合

你说的很准：系统 A 是流水线、系统 B 是交付产物。但两者今天各记各的。真正让 A 能"决策返回哪个 agent 节点"的，不是让 harness 读 transcript 猜（论文证明 LLM 事后归因只有 53.5% 准），而是让 A 和 B 共享一份 Event/Payload 契约 + 因果图，B 的失败沿因果链结构化定位到 A 的责任节点。

判断三自适应要放到流水线"入口"

现在 6 阶段流水线对"生成整条 workflow / 只分析 / 只改一个 agent / 只答疑"一视同仁，仅按 ontology 规模数（rules>60）切换分治深度。论文（AdaptThink / Route-to-Reason / ADaPT / Meta-Reasoner）一致主张：先按问题类型与难度选流水线形状与推理策略，再进入执行。这正是你要的"判断用什么方法"。

判断四不建"内部小本体"——业务契约硬、认知词汇开放

业务层本体（外部输入）只做两件事：投影给理解 + 编译成 wire 契约（直接消灭 output_parse_error）。工厂内部不再引入任何"小本体/认知框架"——分类词汇（系统 kind、emit 语义、意图类型）全部开放（#OPEN-VOCAB），"不忘本体"靠记忆锚点心跳（#ANCHOR）而非结构化框子。蓝图的六图 Micro Ontology Kernel 整体不采纳。

一句话方案：把工厂从"会生成 agent"升级为"会生成能跑通的 agent"——做法是给两套系统装一根 契约脊柱（Contract Spine）：从 ontology 先编译出事件/载荷契约，再让每个 agent 针对契约生成、针对契约校验、针对契约真实执行、失败时沿因果图定点回退。Prompt 编译、Reasoning Router、ask_user 硬化、per-agent 卡片，都挂在这根脊柱上，而不是取代它。

2.2 旧 repo · 6 个手写 agent 为什么真能跑

旧 AO 的招聘链（server/inngest/agents/*.ts）在生产真跑，靠的不是更好的 prompt，而是一层工程韧性——这正是生成 agent 缺的：

分级错误处理

4xx（如 RoboHire 400）→ 捕获、分类 error_code、emit FAILED 事件（不 rethrow）；5xx/网络 → 交给 Inngest 重试。生成 agent 只有 on_error: terminal|soft 声明，没有"业务失败 vs 依赖失败"的分流。

软降级

Neo4j 挂 → rule check 按 fail-close 返回；LLM 超时 → 退到 tier-1 精确匹配。生成 agent 缺乏"依赖不可用时的安全默认"。

载荷契约对账

contract.ts 逐事件核对：producer 实际写的字段 vs consumer 期待的字段 → payload_gap。这正是能消灭 output_parse_error 的机制，新 repo 只在 validate_graph 里做了"字段缺失警告"，没有类型级强校验。

Write-Through 持久化

每个 step.run 完成即写 Postgres（run/activity 行），每步幂等键稳定。这让"哪个 step 产生了什么"可归因——正是结构化回退需要的因果记录。

2.3 生成 agent 真正做对的地方（别丢）

  • 动态规则绑定：rule-gate agent 都带 ontology.fetchActionRules{domain,action}，运行时拉规则，绝不把阈值写死进 prompt。这比旧 repo 把规则埋进 prompt 更先进——蓝图应保留并推广。
  • 结构化 plan[]：每步是可持久化的 manifest action（condition/tool/logic/invoke），带 retries、depends_on、idempotency_key_from、on_error——durability 语义比旧 repo 的散文 actions 更细。
  • 供应商静默降级检测：ProcessResume 的 check-parse-quality 步显式识别"API 成功但关键字段为空 = 解析错误"——这是很成熟的失败语义，值得沉淀进失败本体。

4.1 理解用户问题 · 拆分 · 判断该用什么推理方法

这一支直接回答你的第一个诉求——"根据用户问题和需求，判断用什么方法和思路推理"。一致结论：推理策略与分解深度应按任务难度与执行器能力动态决定，而非静态选一套。

ADaPT · As-Needed Decomposition and Planning 核验
Prasad et al. · NAACL 2024 Findings · arXiv:2311.05772

方法：仅当执行器 LLM 无法直接完成子任务时才递归分解，分解深度自适应任务复杂度与模型能力。

落点：直击 R4。把"1 action = 1 agent"改成"先让 agent 直接尝试该 action，卡住再用已有的 invoke/subflow 拆子 agent"——分解触发器 = 执行失败信号，而非静态规则。天然对应你说的"针对不同 sub-task 再选择是否生成 sub-agent"。

Plan-and-Solve Prompting 核验
Wang et al. · ACL 2023 · arXiv:2305.04091

方法：zero-shot 两段式——先制定"把任务切成子任务"的计划，再逐项执行；诊断三类错误（计算/缺步/语义误解）。

落点：create_plan 用 PS+ 结构化提示；三类错误分类可作为 reflection 阶段"按错误类型选补救策略"的判据（重算/补步/重述需求）。

Route-to-Reason (RTR) · 模型与推理策略联合路由 preprint
Pan et al. · 2025 · arXiv:2505.19435

方法：学习模型与策略的压缩表示，按任务难度在预算约束下于推理时联合选 (LLM, strategy)。

落点：你们已有 34-model gateway 的 model-tier 路由，RTR 把"选模型"和"选推理策略"合并成一个 learned router；训练信号可直接取自 runs 表历史成败 + token 成本。见 §6.2。

Meta-Reasoner · think about how to think 核验
Sui et al. · ACL 2026 (accepted) · arXiv:2502.19918

方法：用 contextual bandit（LinUCB）以当前推理状态的 progress report 为 context，动态选元策略 arm（回溯/换法/重启/澄清/继续）。

落点：把 factory 的 stage 事件 + sandbox 判定编码为 context，arms = revise/re-plan/ask_user/继续，替代现有固定 rule-gate cascade；bandit 权重跨 run 持久化到 agent_memory 持续学习。这正是把"agent loop 是否返工"从写死阈值升级为可学习策略。

DEPS · Describe, Explain, Plan and Select 核验
Wang et al. · NeurIPS 2023 · arXiv:2302.01560

方法：plan→execute→描述回喂→失败自解释→再规划；另配可训练 goal-selector 按"预计完成步数"给候选子目标排序（可行性由学习模块判，不全靠 LLM）。

落点：sandbox 执行回执（code_ran receipts）→ describe/explain → 修订 plan，与 finish-loop 同构。goal-selector 思路 = 用 tool-registry 元数据 + 历史成功率对候选子任务做能力感知排序，避免生成"当前工具集根本执行不了"的 manifest（直击 R4）。

AdaptThink · 学会何时思考 核验
Zhang et al. · EMNLP 2025 Main · arXiv:2505.13417

方法：实证简单任务 NoThinking 优于 deep thinking；用 RL 让模型按难度自适应选 Thinking/NoThinking（长度 −53%、精度 +2.4%）。

落点：为"入口按需求分级推理"提供实证——简单请求走轻量直答路径，复杂请求才升 deep-thinking tier。难度判定本身作为进入 planner 前的第一个路由决策（见 §6.2）。

4.2 澄清式提问 ask_user（解决"泛化提问"）

直接回答你的第二个诉求。一致结论：基模型默认直接给错答案而不主动澄清，必须显式门控；"何时问"要建模、"问什么"要用信息增益选，而非让 LLM 自由生成。

Ask-before-Plan · Proactive Agent Planning 核验
Zhang et al. · EMNLP 2024 Findings · arXiv:2406.12639

方法：提出 Proactive Agent Planning 任务——基于用户对话 + agent-环境（工具）双上下文预测是否需要澄清；Clarification-Execution-Planning (CEP) 三专职 agent；配套 benchmark。

落点："何时问"应同时依赖对话与工具执行反馈——工具报错/空结果本身就是提问触发器（sandbox 回执可直接当信号）。CEP = 把澄清门做成独立 agent 而非单体 prompt。其 benchmark 可做 ask_user gating 的回归测试集。

Active Task Disambiguation · EIG 选题 核验
Kobalczyk et al. · ICLR 2025 Spotlight · arXiv:2502.04485

方法：把澄清提问建模为 Bayesian Experimental Design——选对"可行解空间"期望信息增益（EIG）最大的问题，胜过只在问题空间里让 LLM 直接生成澄清问题。

落点：这是消灭"泛化提问"的直接方案——ask_user 先采样 N 个候选方案（候选 manifest/plan），再问最能区分这些候选的问题。成本 O(NM) 次 LLM 调用，可用小模型采样候选降本。见 §8。

CLAM · Selective Clarification preprint
Kuhn, Gal, Farquhar (Oxford) · 2022 · arXiv:2212.07769

方法：detect→ask→answer 三段式——先显式判定问题是否歧义，仅歧义时才生成澄清问题；实证现成 LLM 默认直接给错答案（被 2024-2026 多篇后续复证）。

落点：ask_user 的最小可行门控就是把"歧义检测"做成独立前置步骤，绝不指望基模型自发提问。其 "adjusted accuracy"（对多余提问计罚）可作为衡量"提问克制度"的量化指标。

CLAMBER · 歧义识别与澄清基准 核验
Zhang et al. · ACL 2024 Main · arXiv:2405.12063

方法：三维八类歧义分类学 + ~12K 样本 benchmark，系统评测 LLM 识别并澄清歧义查询的能力（结论：普遍问不出高质量澄清问题）。

落点：把 taxonomy 编进 ask_user 检测 prompt——先判歧义类别再决定问什么（按类别分派针对性问题模板）；benchmark 离线评测歧义检测组件的召回/精度。

6.1 契约脊柱（Contract Spine）——最高优先级

把"事件 + 载荷 + 能力 + 失败"做成一份小而强类型的契约，作为整个工厂的类型系统。它不是"reasoning ontology"，是"数据契约"。

// 从 ontology 先编译出的事件契约（每个业务事件一条）
type EventContract = {
  name: string;                    // "RESUME_PROCESSED"
  producedBy: string[];            // 哪些 agent emit
  consumedBy: string[];            // 哪些 agent trigger
  payload: FieldSpec[];            // 字段名 + 类型 + required + 来源(ontology 对象.属性)
  taskState?: "submitted"|"working"|"completed"|"failed"|"canceled"; // A2A 式生命周期
};
type FieldSpec = { name:string; type:"string"|"number"|"bool"|"object"|"array"; required:boolean; source:string };
  • 生成期：design_agent 生成 emit 载荷时，用 EventContract.payload 做类型级校验（不只字段缺失警告）——编译期就挡住 R2。
  • 运行期：register.ts emit 前对载荷做契约校验，不合法 → typed reject + 归因，而不是让下游 output_parse_error。这直接复用 message-envelope.ts 已有的 contractFields，只是从"报缺失"升级为"校类型 + 拒绝"。
  • 来源：旧 repo 的 contract.ts（payload_gap）已经证明这条路；A2A 协议给"事件即带状态的任务"提供标准；MetaGPT 给"结构化消息优于对话"背书。

  1. 生成期让 design_agent/codegen_agent 对确定性动作（工具编排、条件分支、载荷组装）置 codeExecuted=true，把生成代码从"脚手架"变"执行体"；LLM 决策步仍走声明式。
  2. sandbox 阶段在 FACTORY_EXEC_GENERATED=1 + -sb 网关下真实执行生成代码（probeAgentModule 先验证可加载），失败自动回退声明式——但把这次回退记为"代码未跑"的证据，而不是当成功。
  3. 验收收紧：acceptanceGate 从"chain 到达终态"升级为"每个非 HITL agent 至少一次真实 sandbox 跑出 schema 合法的下游事件"（用 §6.1 契约校验）。这就是 ORV 里缺的 execution_fidelity 项。

6.5 结构化回退归因（回答"harness 决策返回哪个 agent 节点"）

论文证明 LLM 事后读 transcript 归因只有 53.5% 准。所以别让 harness 猜，用已有的因果记录定位：

  • carry-forward 信封已带 causationId/producedBy/provenance（message-envelope.ts）——交付失败时，沿 causation 链找第一个 emit 违反其 EventContract 的 agent，回退到那个节点。
  • 违约类型直接映射到 Failure 契约（MAST/TRAIL 词表）→ 决定补救策略：契约字段缺失 → 回 design；工具报错 → 回 capability 决策；依赖失败 → 不返工，标 infra；信息缺失 → ask_user。
  • 这把你说的"harness 决策返回哪个节点"从"读日志猜"变成"沿因果图定点"，是结构化的、可复现的。

6.6 补偿与失败语义（让不 happy 的路径也跑通）——直击 R6

  • 生成补偿（SagaLLM / Sagas）：对有副作用的 agent（invite 已发、JD 已发布），工厂自动生成 compensation_event 处理器——manifest 已支持该字段，只是工厂现在不生成。
  • 业务失败 vs 依赖失败分流（借旧 repo 的 4xx/5xx 纪律）：生成 agent 时注入"依赖失败不得写成业务 FAIL"的策略，并把它编进 emit 契约的失败分支。
  • 负例测试合成（TRAIL taxonomy 种子）：test case 不只 happy path，按失败契约生成"空简历/候选人被锁/字段缺失/依赖 down"等负例，让软降级真的被验证过。

7本体使用原则：业务契约硬 · 认知词汇开放

最终定稿（取代本报告早期版本的"小型 Ontology 排序表"）：工厂内部不建任何本体。业务层本体是唯一的本体，它是外部输入，工厂对它只做三个动作——投影、编译、锚定；工厂自己的认知词汇（系统分类、emit 语义、意图类型、修复动作）一律开放，不再有"内部小本体/认知框架"这个概念（蓝图的六图 Micro Ontology Kernel 整体不采纳；早期版本主张的"契约/能力/失败/承诺账本四样小本体"也统一收编为：契约是编译产物、能力是目录查询、失败是开放词表、承诺是折叠幸存文本——都不是"本体"，不需要图、不需要 schema 治理）。

工厂对业务本体的三个动作做什么刚性落点
投影（Project）按当前任务切相关子图给理解/规划——只读，不重建、不复制进内部结构。开放——AI 可质疑、可提出本体没有的概念（ambiguities/修订提案）read_ontology / understand_ontology
编译（Compile）把 event_data 编译成 functions 之间的 wire 载荷契约 + 把规则闸编译成运行时动态拉取。硬——但面积刻意最小：只有权威字段 required、未知类型放行、类型冲突降级 unknowncontract.ts / execution-fidelity / ontology.fetchActionRules
锚定（Anchor）按心跳把本体事实 + 消化结论 + 还欠覆盖重新注入对话——保证长跑不忘，替代"把理解锁进结构"。开放——事实提醒，不指挥ontology-anchor.ts（#ANCHOR）
一句话：本体在工厂里的身份是【外部事实源 + wire 类型系统 + 记忆锚点】，不是【内部认知结构】。刚性只存在于 functions 之间的载荷契约上（那是修 output_parse_error 的钥匙），其余一切认知分类保持开放词汇，随使用生长。
