Agent 工厂 · Ontology-Guided Dynamic Prompt & Subagent Planning 技术架构蓝图报告

本报告给出一套可落地的技术方案：在现有 Agent Factory 的 ReAct conductor、阶段闸门、本体读取、能力解析、沙箱证据和反思记忆之上，加入一个轻量的 Micro Ontology Kernel、Reasoning Policy Router、Dynamic Prompt Compiler 和 Hierarchical Subagent Planner。目标不是把模型锁进 JSON，而是让工厂级 Harness 能动态决定下一步调用哪个 Agent；被调用的 Agent 又能在自己的局部任务内判断是否同步生成 sub-agents 来辅助完成任务；完成后再把证据和结果回传给工厂级调度器，继续选择下一个 Agent，直到生成可部署在 Inngest 上并能跑通的业务 workflow functions。

方案名 Ontology-Guided Adaptive Prompt Factory 接入层 L3a Agent Factory 原则 Free Thinking, Structured Commitment 新增 Dynamic Subagent Planning 优先级 Shadow Mode → Soft Gate → Evidence Gate

0执行摘要

可以，而且非常适合你们这套系统。最优解不是让 AI 每一步临时“凭感觉写 prompt”，也不是把 prompt 模板写死，而是引入一个 Ontology-Guided Dynamic Prompt Compiler：每次内部 Agent、专家、子大脑或设计工具被调用前，系统先生成一份结构化 PromptSpec，再由编译器把本体投影、约束、工具、证据、输出契约组合成最终 prompt。

核心升级
工厂调度与 Agent 内部分工都变成上下文编译产物
关键机制
Ontology Projection + PromptSpec + Linter
控制原则
不约束理解，只约束承诺和交付
最终收益
更接地、更少幻觉、更会组织分工
一句话：小型 Ontology 不应该成为 AI 的“脑子”，而应该成为 Agent 工厂的“工厂级调度账本 + Agent 内部任务账本 + Prompt 编译上下文 + Subagent 分工地图 + 证据索引”。这样每一次 Agent 调用、每一个 prompt/payload、每一次 agent-local sub-agent 任务都可以动态生成，同时不会牺牲模型的开放理解能力。

1.1对照上传蓝图后的补强点

上传的技术蓝图比本报告第一版多了一层非常重要的视角：它不仅看 Agent 工厂这个“生成系统 A”，还把已交付的 runtime functions 这个“业务运行系统 B”放进分析。这个视角提醒我们，Dynamic Prompt Compiler 不应该只服务 design_agent 这类内部生成工具，也应该服务生产函数里的 prompt、外部 AI payload、规则校验输入和审计回放。

上传蓝图强调的点本报告第一版不足强化后的架构处理
系统 A / 系统 B 要分开看主要聚焦 L3a Agent Factory，对已交付 runtime functions 着墨不足。新增“双系统视角”：A 负责编译和生成，B 消费 Prompt/Payload Contract 并回传 Evidence。
7 个 runtime agents 已天然本体化缺少从真实业务链挑试点的路线。将 createJD、ruleCheck、matchResume、interviewInviter 纳入优先试点。
prompt 不只是 system/user 文本PromptSpec 偏内部 Agent 调用，外部 AI payload 没完全覆盖。引入 Prompt/Payload Contract：match、invite、JD 生成请求都进入 ledger。
PromptBlock / PromptInstance 更细有 PromptSpec，但缺可组合 block、实例账本、compilerVersion。补充 PromptBlock、PromptInstance、PromptCompiler 接口和回滚策略。
DSPy / OPRO 式优化提到 telemetry flywheel，但没有把 prompt 改进明确建模为优化问题。新增 PromptPolicy optimizer：用通过率、沙箱失败率、人工介入率、token 成本调 block 顺序和措辞。
失败语义要进入 prompt/payloadEvidence Graph 有失败证据，但缺“业务失败 vs 依赖失败”的 prompt policy。新增 FailureSemanticsBlock，要求 infra failure 不污染业务 FAIL，薄事件回填必须可解释。
版本化和回滚只说 Prompt Ledger，没有强调线上 prompt 静默漂移风险。每个 PromptInstance 绑定 compilerVersion、block ids、outcome，可 diff、canary、rollback。
强化后的结论：Ontology-Guided Dynamic Prompt 不只是“让工厂内部 Agent 写得更好”，而是要把 Agent 工厂生成期和业务运行期统一到同一套 Prompt/Payload Compiler + Ledger + Evidence 闭环里。

1.2Runtime 业务链试点：从 7 个已交付函数切入

2目标形态：Ontology-Guided Adaptive Prompt Factory

目标不是替换现有 conductor，而是在 conductor 内部增加一个“分层认知控制面”：工厂级 Router 根据用户意图、任务阶段、风险、工具需求、验证需求，选择下一步 active agent；active agent 再用自己的局部 Router 编译 prompt、判断是否需要同步生成 agent-local sub-agents，并把结构化证据回传给工厂级调度器。

1. Reasoning Policy Router

决定这一步该用 Direct、Plan-and-Solve、ReAct、GoT-Light、CodeAct、Reflexion、专家评审还是 ask_user。

2. Micro Ontology Kernel

维护 Domain / Capability / Reasoning / Prompt / Evidence 五类小图，作为 prompt 编译和检查的事实来源。

3. Dynamic Prompt Compiler

把角色、任务、子图投影、硬约束、工具范围、输出契约和证据要求编译成最终 prompt / payload。

4. Hierarchical Subagent Planner

区分工厂级 Agent 调度和 Agent 内部 sub-agent 分工：先选 active agent，再由 active agent 判断是否生成局部辅助子脑。

3.1动态 Prompt 编译链路

每个内部 Agent 的 prompt 不再直接来自一个大 system prompt，而是由 PromptSpec 编译出来。模型仍可自由理解和提出方案，但进入工具调用或工程动作前，必须把“要让哪个角色做什么、看哪些事实、受哪些约束、产出什么格式、需要什么证据”提交给 Prompt Compiler。

图 3.1 · 动态 Prompt 编译链路：TaskFrame → PromptSpec → Compiler → Internal Agent

PromptSpec 的价值

字段作用例子
role指定内部 Agent 身份AgentDesigner、RuleReviewer、SandboxRefiner
taskFrame定义这一轮的局部任务“为 MatchResume 生成 Ontology Contract 和 system prompt”
ontologyProjection只给必要子图，降低上下文噪声当前 action、触发事件、产出事件、相关规则、工具候选
hardConstraints必须满足的工程规则不得发明事件；规则必须动态抓；外部副作用必须有幂等键
outputContract约束返回结构，不约束思考过程graphDelta、AgentContract、ReviewFindings
requiredEvidence声明后续要由什么证据证明validate_graph、sandbox receipt、probe result

Prompt 由 9 类 PromptBlock 组成

Block说明例子

EvidenceBlock已经验证的事实。已落库 candidate_id、identity check 已通过、rule audit id。

DataBlock输入数据快照。parsed_resume、job_requisition、clarifications。

FailureMemoryBlock历史失败提醒。“空简历不得继续推进到 match。”

3.2Micro Ontology Kernel

这里的小型 Ontology 不做成重型知识图谱平台，而是做成 Agent 工厂内部的“推理中间表示”。第一版建议只保留五类图，每类图很小，但能覆盖 prompt 生成、检查、证据和学习。

Domain 业务本体

来自 Allmeta / 上传本体 / 本地 fallback。包含 Object、Action、Event、Rule、State，是 prompt 接地的外部世界。

Capability 能力本体

来自工具目录、skills、已有 fleet agents、生产战绩。用于决定复用、组合、新造，以及 prompt 中允许调用哪些工具。

Reasoning 推理账本

记录 Goal、Constraint、PlanStep、Assumption、Risk、Decision、OpenQuestion。它不是思想过程，而是阶段性承诺。

Prompt Prompt 本体

记录 Role、TaskFrame、PromptSpec、ContextPolicy、OutputContract、PromptVersion。让 prompt 成为可审计工件。

Evidence 证据图

记录 validate_graph、code probe、sandbox run、run IO、人工确认、失败反证。finish 只相信证据，不相信宣称。

Failure 失败模式

从 sandbox / review / production stats 回流，连接到具体 AgentSpec、Tool、Capability、PromptSpec，下次设计时自动进入上下文。

3.3Prompt / Payload 双编译

上传蓝图补充了一个容易被忽略的点：很多业务函数并不直接给 LLM 写 system prompt，而是向外部 AI、工具或服务发送结构化 payload。对 Agent 工厂来说，这些 payload 和 prompt 一样，都是“模型/外部智能系统的上下文输入”，也应该被本体接地、版本化、lint 和回流。

Prompt Compiler

面向内部 Agent、规则校验 LLM、生成 JD LLM。输出 system、user、data、outputContract。

Payload Compiler

面向 RoboHire、match API、invite API、外部 AI。输出结构化请求体，并记录字段来源和缺失处理。

Contract Compiler

面向事件、I/O schema、审计和下游消费方。输出事件契约、失败语义、回填策略和人工确认要求。

对象为什么也算 prompt-like必须记录什么
createJD free-text prompt它决定外部 JD 生成模型如何理解需求。字段来源、澄清权重、缺字段策略、compilerVersion、输出质量。
ruleCheck input它决定规则校验 LLM 看到哪些规则、证据和候选人事实。RuleSet 来源、Neo4j 证据、fail-close policy、raw response、audit id。
matchResume payload虽然是 JSON，但它决定外部 match AI 的语义输入。resume/JD 字段来源、ruleCheck 证明、缺字段和薄事件回填。
interviewInviter payload它把业务判断转成外部邀请动作。收件人、时间、模板、业务拒绝 vs 依赖失败、幂等键。
强化原则：只要某段数据会影响 LLM、外部 AI 或业务副作用的判断，它就应该进入 Prompt/Payload Ledger。这样后续失败时不是“重新猜 prompt”，而是可以追到每个字段、规则、证据和 policy block。

3.4Ontology-guided Subagent Planning

这里需要明确校准：我们要的不是单层 Lead Agent 一次性 fan-out 一组 sub-agents，而是 Factory-level orchestration + Agent-local subagent planning。工厂级 Harness 先根据目标、本体缺口、证据状态和阶段闸门推理出“下一个应该调用哪个 active agent”；该 active agent 被激活后，再在自己的局部任务范围内运行局部 Harness，判断是否需要同步生成 agent-local sub-agents 来完成当前 agent 的子任务。agent 完成后返回结构化证据和结果，工厂级 Evidence Gate 再决定下一步调用哪个 agent，直到生成并验证可部署在 Inngest 上的业务 workflow functions。

图 3.4 · 分层模型：工厂级 Harness 选择 active agent，active agent 内部再进行局部 sub-agent planning

两层推理职责

层级核心问题输入输出
Factory-level Harness现在应该调用哪个 agent 来推进整个 workflow？用户目标、全局 BuildPlan、Ontology Proof、上一 agent 的证据、失败模式、Inngest 部署状态。AgentInvocation、下一 active agent、阶段跳转、全局 Evidence Gate 决策。
Agent-local Harness当前 agent 为了完成自己的 task，是否需要生成同步 sub-agents？该 agent 的局部 TaskFrame、局部本体投影、允许工具、任务预算、输出 contract。LocalSubagentPlan、DelegationContract、局部 SynthesisLedger、AgentResult。

3.5AgentRun Contract 与分层证据回流

真正要落地的是一个“调用栈”模型：FactoryRun 选择并启动 AgentRun；AgentRun 可同步启动多个 SubagentRun；sub-agent 结果先汇总成当前 agent 的局部 SynthesisLedger；agent 再输出 AgentResult；工厂级 Evidence Gate 只根据 AgentResult、证据和全局计划状态决定下一步。这样就能形成灵活但可控的智能执行过程。

图 3.5 · 调用栈模型：FactoryRun → AgentRun → SubagentRun → AgentResult → Factory Evidence Gate

AgentInvocation 与 DelegationContract 的区别

契约由谁创建解决什么问题返回给谁
AgentInvocationFactory-level Harness选择并启动下一个 active agent，比如 design_agent、codegen_agent、validate_graph、sandbox_run 或某个已生成的 runtime agent。返回 AgentResult 给工厂级 Evidence Gate。
DelegationContractActive Agent 的局部 Harness当前 agent 内部把自己的 task 拆给 ephemeral specialist、sub-brain、builder 或 promotable runtime sub-agent candidate。返回 SubagentResult 给当前 AgentRun 的局部 SynthesisLedger。
RuntimeAgentContractActive Agent 通过 design_subagent 生成当某个局部能力值得长期复用时，将它升级为可部署、可被父 Agent invoke 的业务子 Agent。返回 AgentSpec / Inngest trigger / invoke contract 给工厂级计划。

2. Run Agent Locally该 agent 是否在自己的内部拆 sub-agents？不拆、轻专家评审、heavy sub-brain、local builder、promotable runtime sub-agent candidate。
3. Collect AgentResult当前 agent 是否完成自己的 contract？产出 AgentSpec、代码、payload contract、验证报告、沙箱 receipt、open gaps。
4. Evidence Gate当前证据是否足以进入下一阶段？advance、retry same agent、call another agent、backtrack、ask_user、finish。
5. Deploy Proof最终生成的 functions 是否能在 Inngest workflow 中跑通？事件链闭合、trigger/invoke contract 成立、沙箱执行通过、失败语义可解释。
设计取舍：这里的智能性来自“每个 active agent 都能局部组织自己的小团队”，而不是工厂一开始就把所有事情拆完。Ontology 的价值是让每一层都知道自己的边界：工厂级看全局 workflow 和部署证据；agent-local 看当前 task 和局部缺口；sub-agent 只看被委派的最小必要上下文。

6Ontology / Prompt Linter

Ontology Linter 不应该一开始就强硬拦截。推荐四级结果：info、warning、blocking、hard_error。探索阶段只提示，设计和交付阶段逐步升级。

9UI 与可解释性

前端不应该展示原始 Chain-of-Thought，而应该展示结构化理由、证据和策略选择。

推理图谱卡片

显示目标覆盖、事件闭合、规则接地、工具接地、证据密度、未解决风险。

Prompt Diff

展示每个 Agent 的 prompt 是由哪些本体片段、约束和证据编译而来，版本如何变化。

Harness Decision

显示为什么这一步选择 GoT-Light / CodeAct / Reflexion，而不是 Direct 或普通 ReAct。

Prompt Block Explorer

按 Role / Goal / Ontology / Evidence / Policy / FailureMemory 展示最终 prompt 的组成。

Payload Contract Viewer

展示外部 AI payload 每个字段来自哪里、是否有证据、缺失时如何 fallback。

Version & Rollback

展示 compilerVersion、PromptInstance outcome、canary 结果，并支持回滚到上一稳定版本。

Agent Invocation Trace

展示工厂级 Router 为什么选择当前 active agent，以及它需要返回什么证据。

Local Subagent Plan Viewer

展示当前 active agent 为什么拆、拆几个、每个局部 sub-agent 的目标、边界、工具和预算。

Factory Evidence Timeline

展示每个 AgentResult 如何推动工厂进入下一 agent、retry、backtrack、ask_user 或 finish。

建议新增 ORV 分数

ORV =
  0.25 * grounding
+ 0.25 * coverage
+ 0.20 * closure
+ 0.20 * evidence_density
- 0.10 * contradiction_debt
指标含义
grounding事件、动作、规则、工具、字段有多少能在本体 / 能力库中找到。
coverage用户目标、业务动作、关键规则被计划和 AgentSpec 覆盖的比例。
closure事件链、IO 链、规则链是否闭合。
evidence_density关键 claim 有多少被 validate、probe、sandbox、人工确认支撑。
contradiction_debt未解决冲突、假设、风险、阻塞问题的数量和严重度。

Phase 3matchResume / interviewInviter把外部 AI payload 纳入 Prompt/Payload Contract，记录为什么带这些字段。缺字段、thin event、外部失败能被 contract 解释，并能触发精准 ask_user。
Phase 4Agent 工厂设计期让 design_agent 生成 Ontology Contract + PromptPolicy，不再只生成 prompt 文本。新造 agents 的 prompt 天然可编译、可 lint、可回流。
Phase 5自优化引入 DSPy / OPRO-style prompt optimizer，根据通过率、人工介入率、沙箱失败率优化 block 顺序和措辞。同类任务 token 更少、失败更少、人工介入更准。

11风险与边界

风险表现缓解
Ontology 约束过强模型过早收敛、创新下降、硬塞类别探索层允许 hypothesis / unmodeled concept；早期只 warning。
JSON 假精确猜测被结构化后看起来像事实所有节点必须有 status、source、provenance、confidence。
Prompt 编译复杂化调试困难，prompt 来源不透明PromptLedger 记录每次 prompt 的组成和版本 diff。
AI 自由写 prompt 导致漂移每次让模型从零写系统提示词，线上行为不可预测AI 只提出/改写 block；compiler 负责组合、lint、版本化和回滚。
Prompt 版本不可控线上 prompt 静默变化，难以解释回归每个 PromptInstance 绑定 compilerVersion、block ids、outcome；支持 canary 和 rollback。
Payload 没纳入账本外部 AI 调用失败后只能看请求体，无法知道字段为何这样选外部 AI payload 与 prompt 一样进入 PayloadInstance 和 Evidence Ledger。
业务失败与依赖失败混淆infra failure 被误写成候选人不合格或业务拒绝Prompt/Payload 必须注入 FailureSemanticsBlock，区分 business reject、dependency failure、data insufficient。
工厂级与 Agent-local 职责混淆局部 sub-agent 直接决定下一步工厂该调用哪个 agentAgent-local sub-agent 只能返回 SubagentResult；下一步只能由 Factory Evidence Gate 决定。
Agent-local sub-agent 过度拆分当前 AgentRun 的简单局部任务被拆成多个子任务，成本和时延上升LocalSubagentPlan 必须先判断 taskShape、parallelizable 和 sharedContextRisk。
Agent-local sub-agent 任务重叠多个局部 sub-agent 调查同一事实，最后 summary 噪声很高DelegationContract 必须声明 ownerAgentRunId、scope、nonGoals、boundary；linter 检查 overlap。
强共享上下文被错误切分每个局部子脑只看到局部，产生互相不兼容的设计对强依赖编码任务优先 active agent + light specialist review，不启用 heavy fan-out。
AgentResult 证据不足active agent 产物看起来完成，但无法推动 Inngest workflow 跑通AgentResult 必须绑定 requiredOutput、evidenceRefs、openGaps 和 recommendedFactoryAction。
Promotable sub-agent 过早产品化临时局部 helper 被误升级成 runtime agent，增加系统复杂度只有具备复用价值、独立触发/invoke contract 和部署证据时，才允许 promote。
Router 滥用高成本 Harnesstoken、时延、sandbox 成本上升默认 escalation ladder；GoT / CodeAct / subagent 需要触发条件。
原始 CoT 暴露污染 UI 和记忆，产生隐私和合规风险只保存 structured rationale summary、证据和决策，不保存原始 CoT。
PII 暴露面扩大为了“更懂上下文”把完整简历到处传DataBlock 按最小必要字段编译；full payload 只进受控审计，敏感字段脱敏或引用化。
Linter 误伤有效方案被错误拦截记录 valid_override_rate、false_positive_rate、Constraint Drag。
Prompt 优化缺评价改了 prompt 但不知道好坏所有 PromptInstance 绑定 outcome：通过率、失败原因、人工介入、沙箱次数、token 成本。

Constraint Drag 指标

为了确认小型 Ontology 是脚手架而不是笼子，建议专门监控：

valid_override_rate

人工或模型推翻 linter 的比例，过高说明规则误伤。

unmodeled_concept_count

模型频繁提出未建模概念，说明 schema 需要扩展。

premature_commit_reverts

过早 commit 后频繁回滚，说明结构化太早。

alternative_plan_count

检查多方案能力是否保留。

novel_capability_proposals

检查是否仍能提出新 tool / skill / sub-agent。

schema_fillers

大量空洞字段、套话字段，说明 JSON 压力太强。

subagent_overlap_rate

子 Agent 输出 claim 的重复率，过高说明分工边界不清。

subagent_marginal_gain

每新增一个子 Agent 带来的新增证据或风险发现数量。

synthesis_conflict_debt

进入 finish 前仍未解决的子结论冲突数量和严重度。

12最终判断

你们这套系统非常适合引入小型 Ontology，但它的正确位置不是“替代模型思考”，而是“管理工厂级 agent 调度、管理 active agent 内部 sub-agent 分工、生成动态 prompt、校验工程事实、索引证据和失败回流”。

最终方案：Factory-level Router 负责“下一步该调用哪个 active agent”，Agent-local Router 负责“当前 agent 是否要同步生成局部 sub-agents”，Micro Ontology Kernel 负责“每一层依据什么事实和证据”，Dynamic Prompt Compiler 负责“把这些东西编译成当前 agent/sub-agent 的 prompt / payload”。四者组合后，Agent 工厂就从“会生成 Agent”升级为“会动态选择 agent、会让 agent 自己组织局部小团队、会用证据一步步生成并验证 Inngest workflow functions”的 Agent 工厂。
