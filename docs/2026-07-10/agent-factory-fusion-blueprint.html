05主管与站长团队采纳蓝图 §03/§04,标注与现有代码的确切嫁接点。核心手法是「减法造主管、升级造站长」——不重写。

  • 主管 = runBrain 的导演半身。保留:回合循环、每回合断点 serializeCtx(conductor.ts:288)、自动压缩(:107)、clarify/approval/boundary park-gates(:517-702)。剥掉:全部 worker 工具。动作空间只剩 {intake, route, delegate, read-artifact, arbitrate-defect, gate, escalate-HITL, finish}。
  • 站长 = 升级的 spawn_subagent。现状是只读研究子脑(14 个只读工具,tools.ts:2352);升级为「角色提示词 + 每站定制工具集」的可写子脑。信任边界从「只读」变为「每站工具面」:监督站只拿只读+归因,编码站拿 codegen/refine,评审站零改码工具。顺序执行,一次一个活跃站长——断点续跑语义不变。
  • 工件门。stageAdmission(conductor.ts:184)从「按工具名准入」泛化为「admit(nextStation, workItem):上游工件在场且门为绿」。编码等 ContractSpec;测试等能编译的 CodeArtifact;finish 等监督+测试签核且 0 阻塞缺陷。
  • 单一多角色提示词必须拆。system-prompt.ts:121 的「一个大脑扮演多角色」是「假团队」根源(蓝图诊断①,核实属实)——拆成 foreman/analyst/coder/reviewer/tester/supervisor 六份角色提示词。UI 侧 process-roles.ts:14 的展示角色恰好能 1:1 映射到真子脑,前端叙事不用改。
  • 返工路由不是盲目重试。红门时读监督者 AuditVerdict.responsibleStation(来自确定性 attributeFidelityFailures:93)把单元打回确切工位;每工位有限返工预算,耗尽升级 ask_user 而非死循环。

06能力梯与技能锻造你的诉求⑤的完整落地——也是对蓝图最大的补充。不是新建:是把仓库里已经存在但蓝图漏掉的技能库,升级成「可实例化」。

先纠正一个事实(包括我自己之前的说法):工厂已有技能层。create_skill(tools.ts:1719)/use_skill(:1764)= {promptFragment(织入 design_agent), recommendedTools, decisionRule, general?},由 DrizzleSkillStore(stores.ts:142)持久化,带 useCount/evalCount/successCount 效果排名(:174-185),sub-agent 也能著技能(共享库)。缺的只是一步:技能今天只能「织入提示词」,不能「生成一个 sub-agent」。

6.1 技能升级:从提示词碎片到可实例化配方

给 Skill 增加可选的 spawnSpec 字段(向后兼容,老技能照常织入):

Skill { // —— 既有字段(不动)—— promptFragment, recommendedTools[], decisionRule, general?, useCount, evalCount, successCount, // 效果统计,已有 // —— 新增:可实例化 —— spawnSpec?: { roleName: string // 「信封解包工」「错误分类审计员」… systemPrompt: string // 完整角色提示词(非碎片) toolAllowlist: string[] // ∩ 派生站长自己的工具面(不越权) strategyDefault: "react" | "reflection" | "debate" exemplarRefs: string[] // 黄金范例锚点(如旧六文件的具体模式) checklist: string[] // 完工自检清单 } }

6.2 能力梯:六级解析,一级比一级贵

任何站长遇到「我需要一个我没有的能力」时,按梯解析(每级都是既有原语,一个新工具 resolve_capability_ladder 把它们串起来并记录决策):

级问题动作既有承载
①已交付函数里有吗?直接复用/组合capability_resolve + FleetCatalog
②工具库里有吗?直接调用search_tools + 全局 registry
③MCP 服务器有吗?折叠为 <server>.<tool> 调用既有 MCP 解析链
④技能库里有可实例化技能吗?instantiate_subagent(skill) → L2 工人SkillStore(升级后)+ spawn_subagent 骨架
⑤都没有?锻造。skill_forge:派一个研究员 sub-agent 调研该能力(读范例/文档/工具目录),写出带 spawnSpec 的新技能 → 回到④实例化create_skill 升级 + 既有研究员派生
⑥能力本质是「缺工具」?造声明式工具再走②create_tool / extract_api_schema(文档→工具)
  • 权限约束:实例化的 sub-agent 工具面 = spawnSpec.toolAllowlist ∩ 派生站长的工具面——技能永远不能给工人越站长之权。锻造出的新技能首次实例化前,若含写权限工具,经 ask_user 确认(主管升级席)。
  • 学习闭环:实例化工人的成败写回该技能的 successCount(既有统计),差技能自然沉底;反思(ports.ts:125)引用技能 id,下次锻造前先读同类失败教训。
  • 诚实边界:这不是自我进化的魔法——⑤级锻造的产物就是一份「角色提示词+工具面+范例锚点」的结构化配方,质量取决于范例与本体;它的价值是把一次性摸索固化为可复用资产,不是发明新算法。

7.1 地面实况:目标形态到底长什么样

事实对生成器的含义
六文件骨架高度规整:注册配置→暂停闸→双日志→信封解包→step 包裹→emit+notify→返回对象,约 30% 可机械生成骨架 = 确定性模板(非 LLM),从 ContractSpec 直接渲染;LLM 不碰样板
step 原语只用了三个:step.run(全部外部调用)、step.sendEvent(出站事件)、step.invoke(仅 resume-parser 同步查重)。无 waitForEvent/cancelOn/并发键生成器动作空间可以收得很窄——三原语覆盖全部目标形态,验收器也只需理解三原语
60-75% 是三类定制逻辑:①字段映射/文本扁平化(40+ 字段 prompt 组装);②错误分类路由(业务 FAIL / 可恢复 park / 不可恢复 emit / 强制持久化 rethrow,六 agent 各不同);③多路径/循环控制流(三路 JR 收敛、双路分叉、fan-out)ContractSpec 的子契约必须显式带三个槽位:fieldMapping、errorTaxonomy、controlFlow——缺槽即 ambiguity,走 ask_user,不许猜
共享基础设施全部「import 不生成」:RoboHire/MinIO/Partner-PG/allmeta/依赖健康分类/通知等都是库调用codegen 带 import-profile(允许 import 的模块清单+签名);profile 有两套:new-AO 运行时(全局工具registry)与 old-AO server(@/lib/*)

7.3 ts_function_module 的生成管线(编码站内部)

  1. 骨架渲染(确定性):从子契约渲染注册配置、暂停闸、日志、信封解包、emit 骨架——扩展既有 specToAgentCode(codegen.ts:105)从「参考渲染」升格为「交付渲染」,撕掉「不直接运行」标签(codegen.ts:138)。
  2. 槽位填充(LLM,范例锚定):三个定制槽各配黄金范例片段(如错误分类槽 → rule-check 的 isInfraFailure park 模式、interview-inviter 的终态码分级);codegen_agent(既有,TS 编译器校验)在骨架内填槽,不重写骨架。
  3. 编译+探针:tsc 严格编译 + 加载探针(泛化既有 probeAgentModule);失败读诊断精修(ReAct)。
  4. 验收(kind 条件化):unit_pass + coverage_met + integration_pass + security_clean(fail-closed)替代 manifest 专用的 chain_ran 判据;code_really_ran 语义沿用——没在隔离里真执行过的代码不许 finish(现有原则,acceptance.ts 延伸)。

首个证明目标(P1 验收):从招聘本体出发,工厂自主生成一个 resume-parser 等价的 ts_function_module(含 step.invoke 查重 + UNPARSEABLE/依赖降级错误路由),在隔离内通过单测+cassette 集成,并在 -sb Inngest 上真跑通一条 RESUME_DOWNLOADED → RESUME_PROCESSED 链。这就是你说的「生成像那六个文件一样的代码」的最小可证版本。

08测试与隔离采纳蓝图 §06 全部(它是对的),此处只记结论与我们的两点强调。

  • P0 事实(核实属实):今天 runGeneratedCode(codeact.ts:135)TS→CJS 后 new Function 同进程执行(:147,159),await handler 无 wall-clock/内存上限(:288),非 runtime import 被 stub 成 {}(:156)。死循环挂 api、带依赖代码测不了——两个 P0 都是真的。

  • 保留两条隔离不变量:FACTORY_EXEC_GENERATED 门(codeact.ts:140)+ -sb 租户串检(:143)——每个新入口都要过。
  • 强调一:worker_thread 不是安全边界(蓝图自己承认)——按测试种类分档隔离是正确权衡,macOS 开发机 vs Linux CI 的信任分裂列入待拍板(§13)。

13诚实风险与待拍板继承蓝图 §13 全部七条(仍然成立),追加融合框架特有的三条新风险与三个待拍板。

新增风险(融合框架特有)

  • 双目标漂移。manifest_agent 与 ts_function_module 两条交付路径若各自演化,验收判据/保真语义会分叉。缓解:验收器只认统一的 AcceptanceReport(kind 条件化是判据集不同,不是两套验收器);契约脊柱(事件/payload)两路共用。
  • 范例过拟合。黄金范例锚定可能让生成器只会写「像旧六文件的招聘 agent」。缓解:范例按模式组织(错误分类模式、fan-out 模式、backfill 模式)而非按文件整体;新领域首单强制走 ask_user 校准三槽位。
  • 技能实例化的权限面。spawnable 技能携带工具面,锻造质量差的技能可能实例化出乱写的工人。缓解:工具面交集约束(永不越站长之权)+ 写权限技能首用 ask_user + 效果统计沉底 + 版本锁定缺陷照常覆盖工人产出。

待拍板(进正式 spec 前)

  • import-profile 的两套目标:ts_function_module 默认生成 new-AO 运行时形态(import 全局工具),还是同时支持 old-AO server 形态(@/lib/*)?后者可直接落进旧仓库,但意味着维护两份 profile。建议:P1 只做 new-AO profile,old-AO profile 作为导出选项后置。
  • ts_function_module 的部署终态:交付 .ts 工件后,「注册为真 Inngest 函数」走哪条路——动态 loader(风险:生产 eval)还是构建期纳入(安全:走既有 manifest-import commit 流程的兄弟通道)?建议:沙箱可动态、生产必构建期。
  • 蓝图既有七条开放问题(工位级归因可靠性、macOS 隔离底座、策略冷启动、ToT/debate 泛化成本、allow-list 供货安全、断点/压缩预算、返工预算调参)——全部仍然有效,原样继承。
