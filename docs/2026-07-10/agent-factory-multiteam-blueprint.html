01现状诊断为什么必须改

先说清楚今天的工厂真实是什么样——否则"多团队+总管"会变成给单大脑贴标签。底层的 QA 机制其实很强（10 判据验收门、三镜评审、独立计划评审、确定性归因、真沙箱行为验证、可断点续跑的 HITL），全部保留；只重建被证实真错的四处。

1
团队是化妆品。 生成是一个单大脑——一条 runBrain ReAct 循环 conductor.ts:294 驱动约 40 个工具，走一个"显示用"的 stage 机；系统提示词让"一个大脑扮演多个角色" system-prompt.ts:121，工具上的 role 只是展示标签 process-roles.ts:14。没有第二个拥有自己上下文/循环/目标的 agent。
2
推理策略是写死的单 ReAct。 唯一的"自适应"是 selectPolicy reasoning-policy.ts:94 选一个流水线形状（full/skinny/analyze/ask_first）+ 模型档位偏置——不是策略选择，没有 CoT/ToT/debate/reflection 的切换。这正是你要补的能力(b)缺的地方。
3
执行沙箱与 agent 格式强耦合，且无超时。 生成代码只能作为 defineAgent 的 .handler 通过 new Function 在同一个 node 进程/事件循环里跑 codeact.ts:135,288，没有任何 wall-clock/内存上限——一个生成的死循环会挂住整个 api；所有非 @agentic/runtime 的 import 被 stub 成 {} codeact.ts:156，所以任意函数和带依赖的代码既跑不了也测不了。
4
交付后质量是被动的。 唯一的生产信号是 fleet 回流 apps/api/.../index.ts:102-185：聚合 14 天失败率、写一条 [生产回流] caveat 笔记，但从不重开任何一次运行。返工闭环不存在。

02架构总览顺序门控装配线 + 独立监督 + 治理闭环

总管在顶层"只指挥不动手"；工件带契约顺序流过 5 个工位，每个工位间是硬门（上游工件在场 + 门为绿）；测试者在真实隔离里执行代码；监督者只读客观证据、提交版本锁定缺陷并按确定性归因把返工打回确切的工位；治理 cron 盯着已交付 fleet，回归超阈值就（经人签核后）重新开环。顺序交接是关键——运行仍是单个 detached driver + 断点续跑，不引入多驱动并发，避免了代码库刻意回避的 Inngest 重平台。

正向流 / 门控交接 归因驱动返工 治理闭环（Inngest cron） 验收门 / 已具备强化
为什么选装配线而不是编排器 fan-out 或黑板并发？ 评审团给"装配线"的 fit_current_arch 打 9 分、并发/durability 风险最低。单工位顺序推进让生成循环留在既有的 detached-driver + 断点续跑底座上，不需要一个代码库刻意回避的多驱动 Inngest 重平台。黑板方案的"四个并发可写子脑共享版本向量"被判为 replay 不安全、并发未解决，已剔除；但它的结构性独立评审与版本锁定缺陷被嫁接过来。

03五个团队 + 总管每个都是真正独立、有自己上下文与目标的子脑

"团队"不再是标签：每个团队是总管派生的、角色专属系统提示词 + 受限工具集的可写子脑（把只读研究子脑 conductor.ts:257,308 升级为可写、角色受限）。团队之间只通过带契约的版本化工件交接。

分析组 ANALYSIS+DESIGN

业务分析师 / 拆解设计师

把原始请求+本体变成机器可校验的拆解：解析意图、深读领域、把目标拆成 N 个带 I/O 签名+验收标准+下游字段契约+声明副作用的子契约，并在写任何代码前独立评审这个拆解。

默认推理ToT→debate（分叉 K 个拆解、打分、再用 critique_plan 挑战胜者）；闭式本体读用 CoT 产出ContractSpec{ deliverableKind, subContracts[], dependencyGraph, ambiguities[] } — 所有下游工位的 v0 工件 复用parseUserIntent · runSpecialists · critique_plan · FleetCatalog

编码组 CODE

编码工程师

取恰好一个子契约，产出满足其签名+验收的通用代码（任意 function/class/module/HTTP handler/CLI 或 defineAgent handler），并在交接前做自己的内联自审。唯一写代码的团队；从不自我判定完成——由评审/监督与总管关闭槽位。

默认推理ReAct(写→编译→读诊断→精修) 外包一层 reflection(designSelfCheck→internalDesignRefine)；返工时切纯 reflection 锁定 span 产出CodeArtifact{ source, compileOk, loadProbeOk, lintClean, version } — append-only 版本，绝不覆盖 复用validateAgentCode · probeAgentModule · design-loop.ts:52,106

评审组 REVIEW · 测前

代码评审员

主观的测前 review-of-coding：在测试者衡量不了的维度上对抗式评审——合规/规则泄漏、上下文契合、元认知完整性——作为快速预筛，让测试者不在明显错的代码上白跑一次真实运行。只发 cite-the-span 结论，从不改代码。

默认推理debate/独立评委：确定性 tier-1 先跑，三镜 LLM 只在 tier-1 沉默处补 产出ReviewFindings[] → revise 打回编码组（版本锁定标注） 与监督者刻意区分：评审=主观/LLM/测前；监督=客观/确定性/测后

测试组 · 测试者 TEST

测试工程师

靠执行代码证明它真的能用且安全：单测（真 c8 覆盖率）、集成（真实输入调用、cassette mock 副作用）、安全（静态 AST + 真实隔离里的动态围堵）。用例作者，经 ask_user 签核领取 fixture/凭据。

默认推理ReAct 驱动 harness + 失败反思；断言/判定引擎确定性且 cassette 锁定，CI 逐位复放 产出TestReport → acceptanceReport 的 kind 条件化判据（unit/coverage/integration/security_clean，后者 fail-closed） 复用/新建verification.ts kinds/Cassette · NEW runGeneratedModule + CodeTester port

监督组 · 监督者 跨生成 + 生产

监督者 · 独立审计

在测试者跑完之后，仅凭客观执行证据独立审计问题：确定性把每个保真度/测试失败归因到责任生产者+建议动作，判断缺陷是否真实，提交总管路由的版本锁定缺陷。也在交付后跑生产证据。从不提出或编写修复——这份独立性正是它的判定可信的原因。它不重跑评审三镜（那是评审组的活）。

独立性全新子脑（只喂工件+契约+证据，绝不喂生产者的思维链）· 物理上没有 codegen/deploy 工具 · 独立 review 模型档 · 只对总管汇报 复用attributeFidelityFailures · evaluateExecutionFidelity · duplicateSideEffectSteps（确定性归因，胜过 ~53.5% 的 LLM 读日志猜测）

04总管 · Foreman只指挥不动手 · 归因驱动返工

总管是 runBrain 的"导演半身"，用减法造出来：保留回合循环、每回合断点 serializeCtx conductor.ts:288、自动压缩、拆解、clarify/approval/boundary park-gates conductor.ts:517-702，但剥掉全部 worker 工具，动作空间只剩 {intake, route, delegate, read-artifact, arbitrate-defect, gate, escalate-HITL, finish}。它从不亲自写工件。

交接门（handoff gates）

把 stageAdmission conductor.ts:184 从"按工具名准入"泛化为"按工件+门准入"：admit(nextStation, workItem) 只在上游输出工件在场 且其门为绿时通过。编码等 ContractSpec；测试等能编译的 CodeArtifact；finish 等监督+测试签核且 0 阻塞缺陷。

返工路由（不是盲目重试）

红门时读监督者 AuditVerdict.responsibleStation（来自确定性 attributeFidelityFailures:93）把单元打回确切那个工位：错接口契约→设计/分析；逻辑 bug→编码；用例不足→测试；坏需求→ask_user。只重置该工位的工件版本，下游须重过每道门。每工位有限返工预算，耗尽则升级 ask_user 而非死循环。

诚实标注（预算内、非免费）： 今天的归因是 agent/event 级；把缺陷映射到工位需要在 join 之上叠一层"契约-归属图"——这是真实工作，分期落地，只在归属模糊时用 LLM 兜底。见 优化点 P2 与 风险。

05监督者的独立性结构性的，不是口号

监督者的判定可信，靠的是四条结构性独立（嫁接自评审团点名的 Blackboard/StationLine/FoundryOS 的皇冠机制）——而非它"承诺"客观。

① 全新子脑

派生时只喂工件+契约+证据，绝不喂生产编码者的思维链/消息历史——所以它无法继承、也无法被生产者的自我合理化说服。

② 只读+归因工具集

拿的是 SUBAGENT_TOOLS 的只读子集，物理上没有 codegen/refine/deploy——它永远不能给自己做的修复自我背书。

③ 独立模型档

跑在专用 review 评审档 model-router.ts:57,89，不是生产者的档位。

④ 汇报线

只对总管汇报，从不向它审计的团队汇报。

评审组 ≠ 监督组。 评审是主观 / LLM 评委 / 测前 / 贴着编码；监督是客观 / 证据锚定 / 测后 / 跨生产。硬 schema + 时序边界隔开两者，避免重复劳动与角色重叠。

06测试者 + 执行沙箱唯一真正吃重的重建

交付物从"Inngest-manifest agent"变成"通用 functions/代码"，测试者必须真的执行任意代码。这落在一个新的 FactoryPorts.codeTester 端口后面，由 SANDBOX stage 里的新 run_tests BrainTool 驱动，让纯 factory 包保持零基础设施。

单测 UNIT

generate_test_cases 扩展为写 vitest 式 function-under-test 断言；runGeneratedModule 执行并报告逐用例 + 真 c8/istanbul 行/分支覆盖率。（今天的"coverage"只是本体动作用例矩阵 test-cases.ts:184）

集成 INTEGRATION

agent 形态走既有 ManifestSandboxDeployer.deployAndObserve:197；纯函数走并行 harness，真实输入调用+断言，副作用经 mock/replay/live cassette 确定性打桩。

安全 SECURITY

静态 AST 扫描 code-lint.ts:161 + 动态围堵：隔离拒绝 fs/net/child_process，egress guard 挡网络，安全用例在运行时断言代码被围住。security_clean fail-closed（未知=阻塞）。

执行环境重建 · runGeneratedModule

今天 runGeneratedCode codeact.ts:135 用 new Function 在同进程/同事件循环跑，要求 .handler 导出，stub 掉所有外部 import，await handler 无任何上限（:288）——死循环挂住 api。重建为一个兄弟函数：

  • 任意导出（function/class/CLI/HTTP handler），不只 defineAgent+.handler。
  • 离开主事件循环，在真实隔离里跑，带硬 wall-clock 超时 + 内存上限（worker_thread + resourceLimits + Worker.terminate；安全/动态与非 JS 用 child_process/容器）——泛化自唯一的真限额原语 runInlineAnalysis inline-codeact.ts:65,80。
  • allow-list 供货依赖：拓宽 {} stub，让真实库能加载并被测。
  • 隔离里采集真 c8/istanbul 覆盖率。
  • 每个新入口都保留两条隔离不变量：FACTORY_EXEC_GENERATED 门 + -sb 租户串检。
诚实边界（也是最大风险）： worker_thread 能封 CPU/内存、修死循环，但不是安全边界（共享进程地址空间）。所以隔离按测试种类分档：单测用快 worker+vm；安全/动态围堵用真 child_process/容器 + egress guard +（Linux CI）seccomp。全部藏在 CodeTester 端口后，底座可从 worker_thread 硬化到容器而不动契约。

07自适应推理策略选择器硬需求(b)的唯一归宿

把 selectPolicy reasoning-policy.ts:94 从"流水线形状+档位偏置路由"升级为双轴选择器：轴1=流水线形状（既有），轴2=AI 自选推理策略。挂在 selectPolicy 已经注入可解释 [推理路线] 引导消息的那个 pre-loop 路由点 conductor.ts:430-460。

两个高度选择

  • L1（总管）：按任务意图给每个工位盖一个默认策略。
  • L2（团队内）：当某个 worker 子脑抛出内部子问题，select_strategy BrainTool 对这个子问题的意图重新分类（嵌套 parseUserIntent），只为这次贡献挑一个策略或一个小 combo DAG。
信号classifyIntentKind（开放词表意图）+ estimateDifficulty（本体难度带）+ ambiguityCount + 请求工位 + 目标工件的开放缺陷类

选择 + 反馈（诚实版）

v1 是确定性可解释策略表（intent, difficulty, station, 子问题形状）→ 策略，只在表低置信时才 LLM 兜底升级。反馈把 policy-learning 的臂从 (pipeline|band) 扩到 (strategy|team|band)——但只加不减、MIN_N 底线：它能把持续制造返工的策略降级，但不探索、不发现新策略。

承重的是手调表 + 策略→原语映射，不是那个"学习者"。 别把它当学习 bandit 卖。

08治理闭环把最大缺口闭上 · 唯一真正 Inngest-durable 的生成侧面

今天生产信号是被动的 caveat 笔记，从不重开跑。重建为一个常驻的定时 Inngest cron（像任意交付物一样注册，继承 durability 纪律 register.ts:152）。

  1. 定时聚合跨 fleet 真实证据：既有 14 天生产失败率 join + 执行保真度回归 + 新冒出的安全发现。
  2. 某交付函数越阈值（复用 total≥3 && failed/total≥0.5）→ 不只写 caveat，而是让同一个独立监督者对近期生产运行归因、定位缺陷。
  3. 经 ask_user 人签核后，调 startRun run-registry.ts:113 开一次 rework run——把生产证据预置成阻塞版本锁定缺陷，运行从责任工位重入流水线，跳过仍有效的工位；finish 重新门控、重新晋升。
幂等（诚实的 Inngest 故事）： cron handler 的聚合读 + "此函数×窗口是否已开过？"记账都在 step.run 里；rework 触发是 idempotent step.sendEvent，keyed on (functionId, window)/rework_run_id（泛化既有 [生产回流] 日期标记去重）——cron 重放或重叠 tick 都不会双开。因为构建期与生产期缺陷共用一套 schema，修复复用整台生成机，不是平行的另一套。

09端到端流程从用户意图到已交付+受监控的代码

  1. INTAKE：用户目标经 startRun 进入；总管跑 parseUserIntent + classifyIntent/estimateDifficulty + capability_resolve/FleetCatalog 复用检查——若已有交付函数覆盖意图，短路到复用/组合。
  2. 策略+分析：双轴选择器盖每工位默认策略；分析组（ToT→debate）产出带类型的 ContractSpec；ambiguity≥2 park 到 ask_user。门(analysis)：评审绿。
  3. 编码：每个子契约总管派生一个编码子脑（ReAct+reflection；编译+加载探针+自审）提交版本化 CodeArtifact。顺序交接，每次提交=断点边界。
  4. 评审（测前）：评审组三镜 cite-the-span 快速主观预筛 → pass 或版本锁定 revise 打回编码。
  5. 测试：测试组写单测/集成/安全用例（真 fixture 经 ask_user 签核），在 CodeTester 隔离里跑（runGeneratedModule + c8 + cassette + egress guard；agent 走 -sb）→ TestReport。
  6. 审计：独立监督者（全新脑、只读证据）确定性归因任何失败 → AuditVerdict 命名责任工位+契约，落成版本锁定阻塞缺陷。
  7. 返工：总管按归因把每个阻塞缺陷打回其工位，限预算；只重置该工位工件版本、下游重过门；缺陷须 Tester 复验才关闭；预算耗尽升级 ask_user。
  8. 门+交付：finish 强制 acceptanceGate（kind 条件化判据 + 0 阻塞缺陷 + 监督&测试签核）；工件作为 durable Inngest 函数或通用供货模块交付；记录成功反思。
  9. 监控+闭环：治理 cron 盯跨 fleet 生产证据，回归越阈值→监督归因→（人签核后）幂等开 rework run，回到责任工位。生成线写入留在断点续跑；cron+交付 agent 是唯二 Inngest-durable 面。

13诚实的风险与开放问题这套设计不回避的地方

最大风险

  • 通用代码执行隔离既是承重重建、也是真正的系统安全问题。 围堵不足→带真实依赖的 LLM 代码逃逸到 api 宿主(worker_thread 不是安全边界)；围堵过度→真依赖加载不了、集成/安全测试变成给未测代码背书的表演。缓解：按测试种类分档隔离、security_clean fail-closed、容器/microVM 底座藏在稳定 CodeTester 端口后作后续硬化期。
  • durability 框架必须诚实。 生成线是同进程 detached 断点续跑驱动，不在 Inngest 上；唯有交付 agent 与治理 cron 是 Inngest-durable。顺序交接避免了多驱动重平台，但可写团队仍放大 park/断点恢复面——半写工件的中途崩溃须靠版本化槽位+工位尝试幂等键对账。
  • 推理策略选择器有变成装饰品的风险：今天只有三个策略(ReAct/reflection/debate)映射到不同代码路径；ToT/CoT/combo 要真实工作。policy-learning 只加不减、不探索——别当学习 bandit 卖。承重的是手调表+策略→原语映射。
  • 归因是 agent/event 级，工位级返工路由在契约-归属图建好并验证前可能把修复派错团队——错路由烧返工预算、侵蚀对闭环的信任。
  • Token/延迟与角色重叠成本：N 个隔离子脑 + debate/ToT 扇出成倍放大成本、返工循环可能死锁；评审-vs-监督必须干净分离(主观测前 vs 客观测后证据)否则重复劳动。缓解：简单/标准带默认便宜单 ReAct、昂贵策略门控给复杂/返工、严格每工位返工预算+ask_user 升级、两个评审角色间硬 schema/时序边界。

开放问题（进正式 spec 前要拍板的）

  • 工位级归因：subContract→station 归属图叠在 attributeFidelityFailures 上能否给出可靠追责，还是 LLM 兜底会频繁到让路由精度成为瓶颈？
  • macOS 开发机隔离底座：seccomp/gVisor 仅 Linux、当前无容器——worker_thread + child_process + egress guard 能走多远，何时容器成为必需，会不会分裂 dev 与 CI 的信任故事？
  • 策略选择器冷启动：只加保守偏置(MIN_N=3)+ 稀疏领域数据下臂很少过底线——需要显式探索预算，还是手调表作承重主体、policy-learning 只作慢速安全降级？
  • ToT/debate 原语泛化成本：critique_plan 是计划专用、runSpecialists 是固定 4 维——把 debate/ToT 做成真一等策略要多少重写 vs 保持预算内跟进？
  • allow-list 供货：哪套依赖被供货给单测/集成，install 步本身如何围堵以防恶意传递依赖在安装期外泄？
  • 断点/压缩预算：版本锁定免压缩缺陷标注须活过自动压缩以保 cited span 有效——长返工循环上会不会撑爆上下文/断点尺寸预算？
  • 返工预算调参：每工位多少返工预算能在收敛与失控 token/延迟之间平衡，超了才升级 ask_user？

契约流水线工厂 · Contract-Line Foundry — 由 4 套独立架构（Loom 编排器 / StationLine 装配线 / Blackboard 黑板 / FoundryOS 内核）经对抗式评审综合而来。脊柱=StationLine（评审团 fit=9、durability 风险最低），嫁接 Blackboard 独立评审+版本锁定缺陷、Loom 减法总管+HITL 升级梯、FoundryOS 确定性归因+治理 cron。

这是设计蓝图，非实现。下一步：定稿 → 正式 spec（docs/superpowers/specs/）→ spec 评审 → 实现计划。所有文件锚点基于当次仓库快照，落地前需再核对。
