# OntoCode 前端设计 Brief（交给设计的完整 Prompt）

> 使用方法：整份文档就是 prompt，直接完整粘贴。示例数据、文案、约束都已内置，不需要额外上下文。

---

## 你的任务

你是资深产品设计师。请为 **OntoCode** 设计一套高保真、可交互的前端原型（首选：单文件 HTML+CSS+少量 JS，深色主题，中文 UI 文案；若你的产出形式是设计稿/画板，请按同样规格出双屏多状态）。

OntoCode 是一个面向企业工程师的工具：**把企业的 Ontology（业务本体：实体/动作/规则/事件）编译成可直接部署上线的 agents 代码（事件驱动的 serverless functions，运行在 Inngest 上）**。用户描述一个业务场景（或者什么都不写、只选一个 Ontology 域），系统一次性生成一组互相接线的 agent、在沙箱里真跑验证、然后一键部署。

---

## 目标用户：FDE（Forward Deployed Engineer，驻场交付工程师）

- 技术很强，日常用 Cursor/Claude Code 写代码；**对聊天式 AI 产品不耐烦**，对黑盒生成器不信任。
- 在客户现场按天交付，最贵的是时间；需要**拿得出手的上线证据**（测试通过、审计记录），因为出事是他背锅。
- 活在 git 里：代码评审走 PR，一切要可导出、可脚本化。
- 一个 FDE 同时服务多个客户（多租户），每个客户一套 Ontology。

**产品的胜负手不是「写代码比 Cursor 好」，而是：读懂客户的 Ontology → 生成接线正确的 agents → 沙箱证据 → 秒部署到受治理的运行时。设计要处处体现「专业工具」而非「聊天助手」。**

---

## 设计语法：类似 Google AI Studio 的操作方式（不是复刻它）

严格遵循这五条操作语法，把它们映射到 OntoCode：

| AI Studio 语法 | 在 OntoCode 中的映射 |
|---|---|
| 单屏工作台，中间是工作对象 | 中间永远是**产物**：描述框 + 生成的 agent 卡片 / manifest / 代码，流式出现 |
| 右侧常驻 Run Settings（全是下拉/开关/分段控件） | 右侧「**生成设置**」面板：Ontology 来源、生成范围、产物形态、模型、交互策略、部署目标、成本预估 |
| 一个主按钮 Ctrl+Enter | **Generate ⌘↵**；完成后右上角 **部署** 按钮点亮 |
| 模型思考是输出区一条可折叠的 Thoughts 条 | 「思考过程」折叠条：默认只显示一行摘要（5 个阶段 × 每阶段一句话），点开才展开，另有「完整 transcript ↗」链接 |
| 左侧窄导航 | 工作台 / 已部署 / 历史 / Ontology 域 / 模板库 / 设置 |

**不是向导（没有 Step 1/2/3），不是聊天（没有对话流）。** 首次生成和第 N 次生成是同一块屏。

---

## 信息架构：整个产品只有两块主屏

1. **工作台**（生成与迭代）
2. **已部署**（Day-2 运维：漂移/健康/修复/回滚）

其余一切（深度日志、推理审计、凭证配置、精修编辑器）都以**外链**形式跳转到平台既有页面，本设计中只出现链接入口，不设计那些页面。

## 屏幕一：工作台（重点演示「第二次生成」时刻）

请设计三个时刻（同一块屏的演进，用顶部或内部控件切换演示）：**空态 → 生成中 → 生成完（增量 diff 审阅）**。其中「第二次生成（增量）」是设计重点，因为迭代才是用户的真实工作流。

### 1. 描述区（composer）

- 多行输入框。空态占位文案：「描述一个场景，或什么都不写——选好 Ontology 来源直接 Generate，OntoCode 会按域里的动作与规则推荐一套 agents…」
- 输入框下方一行 chips：
  - **Ontology 来源 chip**（绿色高亮）：`⬡ RAAS-v1 · 快照 #12 已钉住`（生成基于钉住的 Ontology 快照版本——这是后面漂移检测的基线，要在 UI 上可见）
  - **样例数据 chip**（蓝色）：`◫ 样例数据 · 3（真实简历×2 · 事件×1）`
  - 虚线上传 chip：`＋ 上传 Ontology JSON / 样例 / 文档`
  - 右端主按钮：`Generate ⌘↵`（生成中变红色 `⏹ 停止`；迭代态为 `Regenerate ⌘↵`）
- 空态时输入框下方给**推荐场景 chips**（来自 Ontology 的动作与规则）：「简历投递 → 解析 → JD 匹配 → 高分邀约（HR 审批）」「JD 变更时重算存量候选人匹配分」「面试反馈汇总 → 周报生成归档」，以及一个「最近生成」列表（两行示例：已部署·招聘六件套·6 agents·昨天；草稿·面试反馈汇总·2 agents·3 天前）。

### 2. 预检条（preflight，生成前出现）

绿色轻底横条：`✓ 预检通过 · 覆盖 22/24 动作 · 规则矛盾 0 · 凭证缺失 0 · 快照 #12 与活库一致`，右端小链接「查看未覆盖的 2 个动作 →」。（若预检失败则为琥珀色并给补充建议——可不必设计失败态，但结构要留。）

### 3. 思考过程折叠条（Thoughts）

一行摘要：`▶ 思考过程 · 增量模式：仅重算 3 个受影响节点，其余复用 v3 产物与证据 · 1m02s · ¥0.18 · 完整 transcript ↗`。展开后是 5 阶段的一句话时间线：理解（增量）→ 影响分析 → 生成 3 节点 → 自检 → 增量沙箱。生成中时当前阶段高亮蓝色并带细进度条。**思考过程永远不出现在主区正文里。**

### 4. 输出区（一张大卡，工作台的主体）

**Tab 行**：`变更`（迭代态默认选中）｜`Agents · 7`｜`事件链`｜`Code (TS)`｜`沙箱证据`；右端小链接：`导出 Git PR` · `在 Studio 精修` · `存为模板`。

**diff 汇总条**（变更 tab 下）：`vs 已部署 v3：2 修改 · 1 新增 · 3 未变（复用证据）· 1 手改保护（跳过）· 0 删除`。

**Agent 卡片网格**（两列），每卡：名称 + diff 徽章 + 事件接线（等宽字体：`⚡ 触发事件 → 动作 → ↦ 发射事件`）+ 变更说明 + 操作按钮。示例数据：

| agent | 徽章 | 内容 |
|---|---|---|
| jd-matcher | `修改`（琥珀） | `⚡ resume.parsed → match+score → ↦ match.scored`；变更说明：分数线 ~~score≥80~~ → **score≥75**（假设 A-102 已拍板，覆盖规则 R-087 默认值）；按钮：`↻ 仅重生成此节点` `查看代码 diff` |
| invite-drafter | `修改 · 下游适配`（琥珀） | 触发条件随上游分数线联动更新 |
| background-checker | `新增`（绿） | `⚡ invite.approved → 背调 → ↦ bgcheck.done`；工具 gohireBgCheckApi 需要凭证（联动下方必填项） |
| ats-writeback | `🔒 手改保护`（紫） | 07-20 由 steven 手改（自定义重试逻辑）· 本轮生成跳过，仅提示需人工确认新事件 bgcheck.done 的接入；按钮：`查看我的改动` `解除保护（下轮参与重生成）` |
| resume-parser | `未变`（灰） | 复用 v3 代码 + 沙箱证据，不重复验证 |
| hr-approval-gate / invite-sender | `未变 ×2`（灰） | — |

**代码所有权面板**（卡片网格下方）：文件头 `jd-matcher.ts · [OntoCode 管理 · 生成 #4]` + 说明「直接手改将自动转入 🔒 保护模式（不再被重生成覆盖）」+ 右端「在 Git PR 中审阅 →」。代码区显示 diff（深色代码底），**每个关键分支带溯源注释**：

```diff
-  if (analysis.matchScore >= 80) {   // ← R-087 高分默认线
+  if (analysis.matchScore >= 75) {   // ← 假设 A-102（steven 07-21 拍板）覆盖 R-087
```

### 5. 假设与待定（输出卡底部，琥珀色条 + 展开列表）

条：`⚠ 1 项新假设 · 1 项必填 · 2 项已拍板`，右端按钮「采纳全部推荐」。列表四行：

1. 新假设：「背调在哪一步触发？」→ 选项 chips：`邀约批准后（推荐，依据动作依赖）`（绿色预选）｜`打分后立即`｜`自定义…`（虚线）
2. **必填**（红色）：「背调 API（gohireBgCheckApi）凭证未配置——写副作用，不能替你猜」→ `去 Settings→Integrations 配置`（红）｜`用测试沙箱 key`
3. 已拍板（灰置）：「高分邀约分数线 ≥75」→ 徽章 `已拍板 · steven · 07-21 · 覆盖 R-087`
4. 已拍板：「匹配 API 超时 → 重试 3 次转人工」→ `已拍板 · steven · 07-20`

**交互规则（必须在设计中体现）**：澄清类问题**不阻塞生成**——系统按推荐值先生成完，问题沉淀在这里由用户事后改；**只有「缺凭证」和「写副作用授权」两类是红色必答**。

### 6. 部署条（输出卡最底）

`✓ 增量沙箱 3/3 通过（变更节点 + 下游链路）· 未变节点复用 v3 证据` + 等宽小字 `functionId 不变 ×5 · 新增 raas.background-checker` + 按钮 `导出 Git PR` `触发示例 curl`。其下一行黑底等宽 CLI 行：`CI 同能力 → $ ontocode generate --domain raas --spec spec.md --diff-only --out pr（生成走 PR 评审，UI 只是客户端之一）`。

顶栏右上角常驻主按钮：`部署 v4（3 项变更）`——空态/生成中为置灰，生成完且沙箱通过后点亮（绿色微光）。

## 屏幕二：已部署（Day-2 运维）

此屏**没有右侧设置面板**（中间区全宽）。从上到下四块：

### 1. Ontology 漂移横幅（琥珀色，页面顶部）

`⚠ Ontology 漂移 · 快照 #12（生成基线）→ 活库 #14：新增动作「候选人背调完成回执」· 字段改名 jd.salary → jd.salaryRange`
次行：`影响 2 个 agent：jd-matcher（读取改名字段）· ats-writeback（🔒 手改保护，需人工确认）`
右侧三个按钮：`重生成受影响 2 个 →`（实心琥珀）｜`查看影响明细`｜`本次忽略`（弱化）。

### 2. 部署版本条

卡片标题「部署版本」+ 右注「每版携带：manifest + 代码 + 沙箱证据 + 假设拍板记录（可审计交接）」。横向版本链：`v4 · 当前`（绿框，今天 11:20 · steven · 沙箱 3/3 增量 · 7 agents）← `v3`（07-20 · 沙箱 6/6 · **回滚到 v3** 按钮）← `v2` ← `v1`。

### 3. 运行健康表（24h）

标题右注：「深度监控不在此重复建设 → 跳转现有 Runs / Logs / Reasoning 页」。四列表格：agent / 运行 / 失败 / p95 / 最近失败。示例：resume-parser 142 · 0 · 3.2s；jd-matcher 138 · 0 · 6.8s；**invite-sender 37 · 3（红）· 4.1s · `run-8f2c · 08:42 · GoHire /invite 503`**；ats-writeback 96 · 0 · 1.9s。

### 4. 失败 → 修复回路（本屏的灵魂，重点设计）

红色浅底头部：`失败 → 修复回路 · run-8f2c（invite-sender）：GoHire /invite 连续 503 ×3 后标记失败` + 右端红色按钮 `🔧 带 trace 修复`。展开体：

- **根因**（自动分析，基于 run trace + 代码）：「503 被错误分类为永久错误未进入重试；上游网关抖动场景（trace 第 41 行：retryable=false）」
- **补丁提案**代码框（`invite-sender.ts · 补丁提案 · 含 1 个新增回归用例`）：
  ```diff
  -const RETRYABLE = new Set([429, 502, 504]);
  +const RETRYABLE = new Set([429, 502, 503, 504]); // run-8f2c：网关 503 抖动应重试（指数退避）
  + 新增夹具：gohire-503-then-200.cassette（防回归）
  ```
- 操作：`应用补丁 → 增量沙箱 → 部署 v5`（绿色实心）｜`仅存草稿`｜`去 Runs 深查 ↗`

页脚一行：`假设拍板与版本历史随部署包归档 · FDE 交接零上下文丢失 · 导出交接包`。

## 右侧「生成设置」面板（仅工作台屏，宽约 290px）

分区（每区标题小字 + 控件，全部是下拉/分段/开关，不出现自由文本框）：

1. **Ontology 来源**：下拉 `RAAS-v1 · 快照 #12（钉住）▾`；小链接「⬆ 上传 Ontology JSON · ＋ 添加第二个域（跨域场景）」
2. **生成范围**：分段 `仅受影响（推荐）` | `全量重生成`
3. **产物形态**：分段 `Auto（推荐）` | `Manifest` | `TS Code`（tooltip：Auto=简单节点用声明式 manifest 更稳，复杂逻辑生成 TypeScript，统一以代码视图呈现）
4. **模型**：下拉 `按难度自动分配（默认）▾`
5. **交互策略**（三个开关）：`自动采纳推荐假设`（开，副文案：澄清不暂停；缺凭证/写授权仍必答）；`沙箱验证后才可部署`（开）；`遇每个问题都暂停`（关，副文案：保守模式）
6. **部署与守护**：下拉 `Inngest App：agentic-operator-raas ▾`；开关 `Ontology 漂移检查（每日）`（开）；开关 `失败聚类提醒`（开，副文案：同因失败 ≥3 提示修复回路）
7. 底部预估小字：`本次预估：~¥0.2 · 1–2 分钟（增量 3 节点）` + `本月已用 ¥12.4 / 预算 ¥200`

## 视觉语言

- **深色优先**。参考色板：背景 `#0b0d10`；面板 `#12161b / #171c22 / #1e252d`；描边 `#242c35 / #313b47`；文字三级 `#e9eef3 / #9aa7b4 / #66717d`；品牌绿（主）`#45d19f`；琥珀（假设/漂移/修改）`#e8b34b`；红（失败/必填）`#e5534b`；蓝（进行中/事件/样例）`#5aa7e8`；紫（手改保护）`#b18ae8`。每个强调色配一个 12% 透明度的浅底。
- 圆角偏大（卡片 12–16px，按钮/chip 胶囊形），Material 3 的松弛感，但密度面向专业工具（紧凑行高）。
- 代码、事件名、functionId、CLI 一律等宽字体，代码块用更深的底（`#0d1117`）。
- 徽章语义固定：绿=新增/通过，琥珀=修改/假设/漂移，灰=未变，紫=手改保护，红=失败/必填。
- 主区背景永远干净：不出现连续滚动的日志/思考流。

## 八条设计红线（不该有的——违反任何一条即不合格）

1. ✕ **聊天窗/多轮对话流**：唯一自由文本入口是描述框；没有对话历史、没有气泡。
2. ✕ **向导步骤（Step 1/2/3）**：一块屏演进，没有「下一步」。
3. ✕ **思考流刷屏主区**：思考只有一条折叠摘要 + transcript 外链。
4. ✕ **逐步确认弹窗**：不用 modal 打断生成；澄清后置为假设清单，只有凭证/写授权必答。
5. ✕ **深编辑器嵌进主流程**：只留「在 Studio 精修」外链。
6. ✕ **DAG 拖拽编排画布**：事件链只做只读可视化；编排源头是描述 + Ontology。
7. ✕ **通用 IDE 功能**（文件树/内置终端/多标签编辑器）：代码出口是 Git PR。
8. ✕ **监控大盘**：已部署页只做健康摘要 + 修复回路 + 漂移 + 回滚四件事，深查全部外链。

## 交付与验收

- 交付：单文件 HTML 原型（内联 CSS/JS，无外部依赖），或等价的多画板设计稿。桌面 1440px 为主；≤1000px 允许收纳右栏与图标化左栏的优雅降级。
- 可交互：左导航（或顶部按钮）切换两块主屏；工作台内可切换空态/生成中/生成完三个时刻；Thoughts 条可折叠展开。
- 全部使用上文给定的示例数据与中文文案（真实感是说服力的一部分，不要用 lorem ipsum）。
- **验收清单**：① 5 秒内能看懂「描述 → Generate → 审阅 diff → 部署」主线；② 主区任何状态下都没有日志流；③ 迭代态一眼可见「什么变了、什么没变、什么被保护」；④ 必答项（凭证）与可忽略项（假设）在视觉上一目了然；⑤ 已部署页能在 10 秒内完成「发现失败 → 看到补丁 → 应用部署」的心智路径；⑥ 八条红线零违反。
