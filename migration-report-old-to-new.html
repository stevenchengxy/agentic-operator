01TL;DR

The difference between the two apps is architecture and maturity, not ambition. The old app is a feature-rich monolith welded to the RAAS recruitment domain (Postgres/Prisma + Neo4j + MinIO + multi-Inngest). It is strongest exactly where the new app is empty — it can generate agents from an ontology (the agent-factory, its standout thesis), and it ships a hardened observability/alerting backbone, an LLM-as-judge eval harness, a notification center, copilots, and cross-system trace explorers. The new app is a clean, contract-first, multi-tenant, SQLite/Drizzle, manifest-driven two-process system with strict zero-mock-in-production discipline — but it is demo-stage and has no generation, no monitoring/alerting, no eval suite, no chat, and a flat catalog standing in for an ontology.

Rule 1 — Lift generic infra

Port the hard-won operability backbone the new app lacks (monitor sweep, LLM-judge/calibration, notification engine, trace explorer, AI run-summary, DAG auto-layout). These map onto the new runs/steps/events/tasks/audit_log tables via one new Drizzle ReadPort — drop Prisma.

Rule 2 — Build the agent-factory

The single highest-value net-new build. The new manifest actions JSON already carries the ontology shape the old factory consumed — so v3 graph-verify, v1 deterministic generator, and v2's conductor spine can read the manifest and emit a WorkflowManifest to the existing PUT-workflow path. No Neo4j required.

Rule 3 — Skip vendor/Neo4j/PG-bound

RoboHire/RAAS clients are largely already ported as global tools; partner-Postgres dual-write & raas_mirror are dead in a SQLite world; MinIO maps onto fs tools; the Neo4j entity-writers & AllMeta dependency should be dropped unless the product recommits to a knowledge graph.

06Recommended sequencing

Synthesised from the matrix priorities and the critique's corrections. The hard sequencing constraint: the notification engine is the critical-path root — the sweeper, HITL-stale, triage, boot-crash detector, and the alert center all write into it, so it lands first.

P0 — Operability foundation + the product thesis

  • Notification engine (FIRST) — deterministic derivation + idempotent dedup ingestion + a notifications Drizzle table. The substrate everything else writes into.
  • Monitor sweeper process skeleton — clone demo-runner.ts lifecycle (env gate, NODE_ENV=test no-op, unref timers, graceful shutdown, heartbeat). Lowest-risk, highest-certainty port.
  • Monitor sweep backbone — port + dedup/auto-resolve over a new Drizzle ReadPort on runs/steps/events/tasks.
  • Agent Factory v3 (graph compile + verify) — pure, tested, tiny; verify DAG closure before any generation reaches PUT-workflow.
  • Agent Factory v1 (deterministic-backbone generator + reflexion loop) — gated on a data-readiness prerequisite: enrich the manifest/entity_types/event_types with the per-action grounding the old generator read from Neo4j.

P1 — Generation depth, eval, and observability surfaces

  • Agent Factory v2 conductor spine (ledger + Bus→SSE + re-plan/smoke/self-repair) — migrate the deterministic spine, re-evaluate the cognition builders.
  • Ontology→Agent deriveAgents analyzer (the engine v1/v2/v3 stand on).
  • LLM-judge eval harness + judge calibration (Cohen's κ) + drift; and a scenario-based regression harness (golden-set, fine-grained failure taxonomy) to validate factory output.
  • Domain-agnostic rule-check quality-gate primitive (fail-closed; infra-failure ≠ rejection).
  • DAG auto-layout (Sugiyama-lite) — generated agents need positions; cross-system trace explorer; AI run-summary (+ new run-detail tab); run-scoped copilot; threshold monitors; HITL-gate hardening.
  • Honest-degradation LLM-fallback convention — one shared helper over the gateway (cache→assemble→call→parse→persist, mandatory deterministic branch), depended on by ~6 items.

P2 — Operator tooling & depth (some gated on RBAC)

  • Production RBAC / admin gate (prerequisite, surfaced from the critique) — the old factory-auth timing-safe gate is the ready pattern. Blocks env-config + control-plane mutations.
  • Env-config UI (behind RBAC), agent-config versioning/snapshots, boot/crash liveness, analytics aggregation, alert triage, dependency-health judge, notification channels, neighborhood graph, external-API forensic log, candidate-lock-as-tool, ontology-gen prompt assembler.

P3 / Skip — Lower-value or domain-bound

  • Build later: global copilot, notification/alert center UI, events-bus multiplexer, fleet enhancements, per-tenant funnel, entity journey.
  • Skip: old i18n (redundant), RoboHire clients (done), RAAS bridge (webhooks supersede), AllMeta/Neo4j writers, partner-PG + raas_mirror + recruitment roster metadata, datasources/mock-raas page (violates zero-mock rule), confirmed dead code.

        The one caveat that changes P0 sizing

        The factory thesis "no Neo4j needed — read the manifest" is true for graph topology (triggers/emits) but not for the rich grounding (object/field schemas, rule guards, emittable payload shapes) the old prompt-synthesis was built around. The live RAAS v5 manifest has empty input_data:{} and no tool_use[] on its actions — so the deterministic backbone has thinner grounding than the old path assumed. Treat "enrich the catalogs/manifest with per-action grounding" as a data-readiness gate on Factory v1, not an afterthought.

Verdicts are recommendations, not commitments — confirm each "already exists" UI anchor and the manifest data-readiness gate before scheduling.
